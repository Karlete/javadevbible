Dependencies Management

How Maven resolves transitive dependencies — and what to do when it resolves them wrong

← Back to Index
📋 Contents

What Are Transitive Dependencies?

When you declare a dependency on library A, and A itself depends on library B, Maven automatically resolves and downloads B too — you never declare B yourself. This is transitive dependency resolution, and it's what makes a single spring-boot-starter-webmvc declaration pull in dozens of actual JARs.

The problem it creates: in any real project, multiple libraries transitively depend on different versions of the same artifact. Two different libraries might each want a different version of httpclient5. Maven has to pick exactly one — this page is about understanding how it picks, and how you take control when it picks wrong. For basic dependency syntax and scopes, see Dependency Scopes; for the full POM structure, see POM.xml Structure.

The examples come from the shop, a Spring Boot 4 application that also talks to two outside services through their client libraries: parcelexpress-client for shipping rates and ledgerline-tax-client for VAT. Both are invented for this page; the conflict they cause is not.

How Maven Resolves Version Conflicts

When the dependency graph contains two different versions of the same artifact, Maven applies "nearest definition wins" — not "newest version wins", which surprises almost everyone the first time they hit it.

/*
 *  shop
 *  ├── ledgerline-tax-client:2.3.0 ──▶ httpclient5:5.4.1   (depth 2)
 *  └── parcelexpress-client:1.8.0  ──▶ httpclient5:5.1.3   (depth 2)
 *
 *  Same depth → first declared in YOUR pom.xml's <dependencies> wins.
 *  If ledgerline-tax-client is declared first, 5.4.1 wins —
 *  NOT because it's newer, but because of declaration order.
 *  Swap the two declarations and the shop silently runs on 5.1.3.
 *
 *  Different depths:
 *  shop
 *  ├── httpclient5:5.4.1                                       (depth 1 — DIRECT)
 *  └── parcelexpress-client:1.8.0  ──▶ httpclient5:5.1.3       (depth 2)
 *
 *  Depth 1 (direct dependency) ALWAYS wins over depth 2+, regardless
 *  of version. This is the most reliable way to force a version:
 *  declare it directly in your own pom.xml.
 */
# See exactly what won and what got overridden ("omitted for conflict")
mvn dependency:tree -Dverbose

# Output excerpt:
# [INFO] +- com.ledgerline:ledgerline-tax-client:jar:2.3.0:compile
# [INFO] |  \- org.apache.httpcomponents.client5:httpclient5:jar:5.4.1:compile
# [INFO] \- com.parcelexpress:parcelexpress-client:jar:1.8.0:compile
# [INFO]    \- (org.apache.httpcomponents.client5:httpclient5:jar:5.1.3:compile - omitted for conflict with 5.4.1)

Three ways to take control — in order of preference

// 1. ✅ BEST: declare the version directly — depth 1 always wins
<dependency>
    <groupId>org.apache.httpcomponents.client5</groupId>
    <artifactId>httpclient5</artifactId>
    <version>5.4.1</version>
</dependency>

// 2. ✅ BEST AT SCALE: pin it project-wide via dependencyManagement —
// no need to also add it as a direct dependency, applies to ALL modules
<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>org.apache.httpcomponents.client5</groupId>
            <artifactId>httpclient5</artifactId>
            <version>5.4.1</version>
        </dependency>
    </dependencies>
</dependencyManagement>

// 3. Last resort: exclude it from the offending parent and declare separately —
// more maintenance burden (you must remember to re-declare it)
<dependency>
    <groupId>com.parcelexpress</groupId>
    <artifactId>parcelexpress-client</artifactId>
    <exclusions>
        <exclusion>
            <groupId>org.apache.httpcomponents.client5</groupId>
            <artifactId>httpclient5</artifactId>
        </exclusion>
    </exclusions>
</dependency>
A silently-resolved conflict is not a solved conflict

Maven will always pick a version and build successfully — it never fails the build just because of a version mismatch. That means a binary-incompatible API change between 5.1.3 and 5.4.1 can compile fine and explode at runtime with NoSuchMethodError, far from wherever the actual conflict originated. Treat any unexpected entry in dependency:tree -Dverbose as something to actively verify, not ignore because the build went green.

Importing a BOM

A Bill of Materials is a pom-packaged artifact containing only dependencyManagement — a coordinated set of version pins published by a project so consumers never have to guess which versions work together.

spring-boot-starter-parent vs importing the BOM directly

When you inherit from spring-boot-starter-parent, you get the Spring Boot BOM and plugin defaults and resource filtering — but a project can only have ONE <parent>. If your project already has its own parent (a company-wide parent POM, for example), you can't also parent from Spring Boot. The fix: import spring-boot-dependencies as a BOM instead of inheriting from spring-boot-starter-parent — you get the version management without giving up your own parent.

Practical Exclusion: Swapping an Embedded Server

The classic real-world exclusion isn't fixing a conflict — it's swapping out a transitively-included implementation for an alternative.

Version Ranges — and Why You Shouldn't Use Them

// Maven supports mathematical version ranges
<version>[1.0,2.0)</version>   <!-- >=1.0, <2.0 -->
<version>[1.5,)</version>     <!-- >=1.5, any upper bound -->
<version>(,2.0]</version>     <!-- <=2.0 -->
Avoid version ranges in production builds

A range means the exact resolved version can change between builds without any change to your pom.xml — the build is no longer reproducible. The same commit can produce different binaries depending purely on when it was built. Pin exact versions (via properties or a BOM) and update deliberately with mvn versions:display-dependency-updates instead of letting the range silently drift.

Diagnostic Commands Reference

# Full dependency tree with conflict resolution shown
mvn dependency:tree -Dverbose

# Filter to one artifact — find where it's coming from
mvn dependency:tree -Dincludes=org.apache.httpcomponents.client5

# Declared-but-unused, or used-but-undeclared dependencies
# (the latter is a real risk: it compiles because of a transitive dependency
# that could disappear if an unrelated library changes)
mvn dependency:analyze

# Pull down sources/javadoc jars for IDE navigation
mvn dependency:sources
mvn dependency:resolve -Dclassifier=javadoc

# Check for newer available versions across all dependencies
mvn versions:display-dependency-updates

Interview Questions

🎓 Junior level
What is a transitive dependency?

A dependency of a dependency. If your project depends on library A, and A depends on library B, B is pulled in automatically as a transitive dependency — you never declare it yourself.

What does the exclusions element do?

Prevents a specific transitive dependency from being pulled in by a declared dependency. Common uses: removing a conflicting/vulnerable version, or swapping an implementation (excluding Tomcat to use Jetty instead).

What does mvn dependency:tree show, and when do you reach for it?

It prints the resolved dependency graph: every artifact that ends up on the classpath and which direct dependency pulled it in. You reach for it the moment a class appears that you never declared, or a library runs at a version you did not expect. -Dincludes=org.slf4j filters the output to one group, and -Dverbose also lists the versions that lost a conflict, which is how you see that two paths asked for different versions of the same jar.

🔥 Senior level
Explain "nearest definition wins" and why it can silently select the wrong version.

Maven resolves version conflicts by depth in the dependency tree — the shallowest declaration wins, regardless of which version is actually newer or more correct. A direct dependency (depth 1) always beats a transitive one (depth 2+). At equal depth, declaration order in the POM decides. This means adding an unrelated dependency that happens to declare an old version of a shared library, earlier in your POM, can silently downgrade something you rely on — with no warning, since Maven always resolves to some version and builds successfully regardless of binary compatibility.

Why prefer dependencyManagement over a direct exclusion+redeclare for fixing conflicts?

dependencyManagement applies the pin project-wide (or across an entire multi-module reactor if declared in the parent), automatically, for every current and future dependency that transitively pulls in that artifact — no exclusions needed anywhere. Exclusion+redeclare only fixes the one dependency you applied it to; if a second, unrelated library later pulls in the same conflicting version, you'd need to repeat the exclusion there too. It doesn't scale and is easy to forget.

What does importing a BOM actually do, and what wins when two BOMs manage the same artifact?

A dependency with <type>pom</type> and <scope>import</scope> inside <dependencyManagement> copies the BOM's managed versions into your own dependencyManagement. It adds no dependency to the classpath; it only decides the version of artifacts you declare without one. Versions you manage yourself in the same POM override imported ones, and between two imported BOMs the one declared first wins. That ordering matters in practice: importing the Testcontainers BOM after the Spring Boot one means Boot's managed Testcontainers version is used, not the one you meant to pin.

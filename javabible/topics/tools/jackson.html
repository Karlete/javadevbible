Jackson 3 — JSON in Java

How Jackson 3 maps Java records to JSON in Spring Boot 4: JsonMapper, java.time, custom serializers, @JsonView and the defaults that changed from Jackson 2.

📋 Contents

What is Jackson, and Why Does Every Spring Project Use It?

Jackson is a Java library for processing JSON — converting Java objects to JSON (serialisation) and JSON back to Java objects (deserialisation). It is not part of the JDK, not a Jakarta EE specification and not written by Spring: it is an independent open-source library that became the default because it is fast, needs no configuration for the common case, and every major Java framework integrates it.

The problem it solves is the one every HTTP API has: the wire format is text, the program works with typed objects. Writing that translation by hand means escaping quotes, handling null, nesting objects and arrays, formatting dates — on every endpoint, and differently each time.

Jackson 3 is what Spring Boot 4 uses

Spring Boot 4 moved to Jackson 3. Its group id and Java packages changed from com.fasterxml.jackson to tools.jackson, the mapper became immutable, its exceptions became unchecked, and several defaults changed. The annotations (@JsonProperty, @JsonFormat, …) did not move: jackson-annotations keeps its 2.x coordinates and com.fasterxml.jackson.annotation package, and is shared by Jackson 2 and 3. Most tutorials online still show Jackson 2; this page shows Jackson 3 and says where it differs.

ModuleCoordinates (Jackson 3)What it does
jackson-core tools.jackson.core Low-level streaming API (JsonParser, JsonGenerator) — you rarely use it directly
jackson-databind tools.jackson.core JsonMapper and data binding — "Jackson" for 99% of uses. Since 3.0 it includes java.time, Optional and parameter-name support, which were separate modules in Jackson 2
jackson-annotations com.fasterxml.jackson.core (unchanged) The @Json* annotations, pulled in by databind

JsonMapper — Built Once, Immutable, Shared

In Jackson 3 ObjectMapper (and its JSON subclass JsonMapper) is immutable. All configuration happens on a builder; there are no setters to call on a live instance, so a mapper can no longer be reconfigured by one part of the code while another is using it.

// Everyday operations
String json = mapper.writeValueAsString(order);
OrderResponse parsed = mapper.readValue(json, OrderResponse.class);

// Generic types need a TypeReference: List<OrderItemResponse>.class does not exist
// at runtime (type erasure), so the anonymous subclass captures the full type
List<OrderItemResponse> items =
        mapper.readValue(json, new TypeReference<List<OrderItemResponse>>() {});

// Tree model for JSON whose shape you do not control (a webhook, a vendor API)
JsonNode root = mapper.readTree(webhookBody);
String status = root.path("data").path("status").asString();
A new mapper per request is a real performance bug

Building a mapper is expensive: it resolves features and builds internal caches of serializers for every type it meets. Those caches are what make the second call fast. Creating a mapper per request throws them away every time. A built mapper is thread-safe — in Jackson 3 it is immutable — so share one: in a Spring application, inject the JsonMapper bean Spring Boot already configured.

Core Annotations

Annotations change how one type is mapped. They live in com.fasterxml.jackson.annotation (unchanged in Jackson 3), except the few that name databind classes — @JsonSerialize, @JsonDeserialize, @JsonNaming — which moved to tools.jackson.databind.annotation.

The best @JsonIgnore is a field that is not there

Jackson 2 tutorials put @JsonIgnore on a passwordHash field of the entity being returned. The safer design is a response record that never had that component: a forgotten annotation cannot leak something the type does not contain. Keep @JsonIgnore for derived or internal values on types that really are shared. For a default that applies to every type, Spring Boot exposes spring.jackson.default-property-inclusion=non_null instead of annotating each class.

Records and Jackson

Records are the natural DTO for JSON: immutable, no setters, every value passed through the canonical constructor. Jackson deserialises a record by calling that constructor, matching JSON property names to component names. Those names are stored in the class file's Record attribute, so records never needed the -parameters compiler flag or an extra module.

Regular classes with constructors

For a non-record class bound through its constructor, Jackson needs the parameter names. Jackson 3 detects them by default (MapperFeature.DETECT_PARAMETER_NAMES, the former ParameterNamesModule) when the code was compiled with -parameters, which the Spring Boot Maven and Gradle plugins configure. Without it, annotate the constructor with @JsonCreator and each parameter with @JsonProperty.

Date and Time — Which Type, Not Which Module

In Jackson 2 the classic production bug was a missing JavaTimeModule or a date written as an array of numbers. Jackson 3 removes both: java.time support is built into databind and ISO-8601 strings are the default. The decision that is left is the important one — which java.time type the API exposes.

TypeWritten asUse for
Instant"2026-11-25T09:30:00Z"A moment in time: Order.placedAt, Customer.createdAt
OffsetDateTime"2026-11-25T10:30:00+01:00"A moment plus the offset the user saw, when that offset matters
LocalDate"2026-11-25"A calendar date with no time: an estimated delivery day
LocalDateTime"2026-11-25T10:30:00"Rarely right in an API: no zone, so a client cannot tell when it happened
LocalDateTime in an API is a time-zone bug waiting to happen

"2026-11-25T10:30:00" is ten thirty somewhere. A shop server in UTC and a customer in Madrid read it an hour apart, and nothing in the JSON says which reading is right. Store and expose moments as Instant (written with a trailing Z) and let the client format them in the user's zone.

Spring Boot Auto-Configuration — What You Get and How to Change It

With Jackson on the classpath, Spring Boot 4 auto-configures one JsonMapper bean and uses it for every @RestController request and response. These Jackson 3 defaults are the ones a Jackson 2 codebase notices:

FeatureJackson 3 defaultWhat it means for the shop's API
FAIL_ON_UNKNOWN_PROPERTIES false A client sending a field the record does not have is not rejected — additive API changes stay compatible
WRITE_DATES_AS_TIMESTAMPS (now a DateTimeFeature) false ISO-8601 strings, not epoch numbers
FAIL_ON_NULL_FOR_PRIMITIVES true A missing int quantity is an error, not a silent 0
FAIL_ON_TRAILING_TOKENS true {"sku":"KB-104"} garbage is rejected instead of half-read
SORT_PROPERTIES_ALPHABETICALLY true Properties without an explicit @JsonPropertyOrder may be written in a different order than with Jackson 2 — a test comparing raw JSON strings may need updating
DEFAULT_VIEW_INCLUSION false With a @JsonView active, unannotated properties are left out (see below)
Customise Boot's mapper — do not replace it

Declaring your own @Bean JsonMapper (or JsonMapper.Builder) disables Boot's auto-configuration of the mapper entirely, including every spring.jackson.* property. To add to Boot's configuration instead, declare a JsonMapperBuilderCustomizer; it receives the builder Boot has already prepared. It replaces Jackson 2's Jackson2ObjectMapperBuilderCustomizer, which only survives in the deprecated spring-boot-jackson2 module.

Custom Serializers and Deserializers

Write one when the default output for a type does not match the API contract: masking personal data, a legacy format you must accept, or a value type Jackson cannot see into. Jackson 3 renamed the base classes — JsonSerializer → ValueSerializer, JsonDeserializer → ValueDeserializer, SerializerProvider → SerializationContext — and the methods no longer declare IOException.

A per-field annotation suits a one-off. When a type should always be written the same way, register the serializer once in a SimpleModule through a JsonMapperBuilderCustomizer, as in the previous section.

@JsonView — Different Fields for Different Contexts

@JsonView defines named views and marks which properties belong to each. Two endpoints can return the same record with different fields, without a second DTO.

@JsonView vs separate DTOs

@JsonView fits when two endpoints return the same data with different visibility — same query, same object. Use separate records when the data differs: a list view backed by a lighter query, or a back-office view that joins more tables. A record with four views on every component is harder to read than two small records.

Jackson in Tests

Test what Jackson does, not just what the controller does

A plain unit test of serialisation catches the bugs that otherwise surface when a client complains: a field that should be hidden appearing, a date in the wrong shape, a property renamed by a naming strategy. It also catches a dependency upgrade that changes a default — exactly what a Jackson 2 → 3 migration does.

Best Practices

✅ Do
  • Inject the JsonMapper Spring Boot configured, and change it through spring.jackson.* or a JsonMapperBuilderCustomizer
  • Return records designed for the API, never JPA entities: no lazy-loading surprises, no fields that were never meant to leave the server
  • Expose moments as Instant; use LocalDate only for real calendar dates
  • Use the tree model (JsonNode) for third-party payloads whose shape you do not own, and map only what you need
  • Pin JSON output in unit tests for every type whose shape is part of a contract
  • When migrating from Jackson 2, remove the com.fasterxml.jackson.datatype modules and use spring.jackson.use-jackson2-defaults only as a temporary bridge
❌ Don't
  • Don't create a mapper per request or per method call — it throws away Jackson's serializer caches
  • Don't declare your own @Bean JsonMapper just to change one feature: it switches off all of Boot's Jackson configuration
  • Don't mix com.fasterxml.jackson.databind and tools.jackson.databind imports in your own code — two mappers with two configurations
  • Don't rely on JSON property order or compare raw JSON strings in tests; compare parsed values
  • Don't put @JsonView on everything to avoid writing a second DTO when the data really differs
  • Don't use LocalDateTime for timestamps in an API

Interview Questions

🎓 Junior level
What is Jackson, and what is JsonMapper?

Jackson is the de-facto Java library for JSON. JsonMapper (the JSON flavour of ObjectMapper) is its entry point: it serialises objects to JSON and deserialises JSON into objects. Spring Boot auto-configures one as a bean, and Spring MVC uses it for every @RestController request and response body.

What does @JsonProperty do, and how is it different from @JsonAlias?

@JsonProperty("full_name") sets the name used in both directions: the property is written and read as full_name. @JsonAlias only adds extra names accepted when reading; output still uses the main name. Aliases are useful while clients migrate from an old property name to a new one.

Why don't Jackson calls need a try/catch or a throws clause in Jackson 3?

Jackson 3 made its exceptions unchecked: JacksonException (which replaced JsonProcessingException) extends RuntimeException. Invalid input still throws, but the caller decides where to handle it — in a Spring MVC application, usually a @RestControllerAdvice that turns it into a 400 ProblemDetail.

Which java.time type should an API use for "when was this order placed"?

Instant. It is an absolute moment and is written as an ISO-8601 string ending in Z, so every client reads the same point in time. LocalDateTime has no zone, so the same JSON means different moments to a client in Madrid and a server in UTC.

🔥 Senior level
Why is creating a new mapper per request a performance problem?

A mapper builds and caches a serializer and deserializer for each type it meets; that cache is what makes later calls cheap. A new mapper per request rebuilds that work every time and creates garbage under load. A built mapper is thread-safe — in Jackson 3 it is immutable — so one shared instance (the Spring bean) is the correct pattern.

How do you customise Spring Boot's JSON configuration without replacing it?

Through spring.jackson.* properties, or a JsonMapperBuilderCustomizer bean that receives the builder Boot has prepared and adds modules or features to it. Declaring your own JsonMapper or JsonMapper.Builder bean disables the auto-configuration of the mapper entirely, so every Boot default and every spring.jackson.* property silently stops applying.

What breaks when a Spring Boot 3 application moves to Spring Boot 4 and Jackson 3?

Imports: databind and core move from com.fasterxml.jackson to tools.jackson (annotations stay). Code that configured a mapper with setters or registerModule must use the builder; custom serializers extend ValueSerializer / ValueDeserializer; Jackson2ObjectMapperBuilderCustomizer becomes JsonMapperBuilderCustomizer. Behaviour changes too: missing primitives and trailing tokens now fail, properties may be sorted, and unannotated properties disappear under a @JsonView. spring.jackson.use-jackson2-defaults=true eases the upgrade but cannot reproduce every old default.

What does FAIL_ON_UNKNOWN_PROPERTIES=false give you, and when would you turn it on?

With false (the Jackson 3 default), unknown JSON properties are ignored, so adding a field on the client side does not break an older server — additive API evolution stays safe. Turn it on for strict contracts where an unknown key almost always means a typo: configuration documents, or an internal API where silently dropping a misspelt field would hide a bug.

What is @JsonView, and when are separate DTOs the better choice?

@JsonView controls property visibility per endpoint, so the same record can be written differently for a public and a back-office endpoint. It fits when the data is the same and only visibility differs. When the query, the shape or the service call differs, separate records are clearer. Since Jackson 3 sets DEFAULT_VIEW_INCLUSION to false, a property without a view is excluded whenever a view is active.

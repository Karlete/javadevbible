Caching with Redis in Spring Boot

The product page is read thousands of times for every time a product changes. Caching it in Redis takes that load off PostgreSQL — and brings the two hard questions with it: when does a cached product stop being true, and how do three replicas agree on it

Checked against Spring Boot 4.2 · Spring Data Redis 4.2 · Redis 8 — November 2026

What a Cache Is — and Why the Shop Needs a Shared One

A cache keeps the result of an expensive operation so the next request can reuse it instead of repeating the work. Redis is an in-memory key-value store, reached over the network, that every replica of the shop can share. Spring's cache abstraction lets a method say "cache my result" with an annotation, and Spring Boot plugs Redis in behind it.

The problem it solves is repeated work on data that changes far less often than it is read: product details, category listings, prices. The usual first attempt is a map inside the service — which works on one instance and quietly breaks on three.

Setting Up the Cache

Two starters and one annotation: @EnableCaching switches the abstraction on, and with Redis on the classpath Spring Boot auto-configures a RedisCacheManager as the cache behind it.

For local development, add Redis to the Compose file (redis:8.12); for tests, start it with Testcontainers and @ServiceConnection, as with PostgreSQL. Valkey, the open-source fork of Redis, speaks the same protocol and works with the same client.

Store JSON, Not Java Serialization

By default the Redis cache stores values with Java's built-in serialization. That requires every cached class to implement Serializable, ties the stored bytes to the exact class version — so a deployment that adds a field can fail to read what the previous version cached — and the Spring Data Redis documentation warns that Java deserialization of untrusted data can lead to remote code execution. JSON avoids all three.

Code review comment

@Cacheable(cacheNames = "products", key = "#sku")
public Product findEntity(String sku) { ... }
@Cacheable(cacheNames = "products", key = "#sku")
public ProductDetails details(String sku) { ... }

Let's not cache the JPA entity. It drags Hibernate proxies and lazy collections into the serializer, and whatever comes back from the cache is a detached object that looks managed. Cache the record the API returns — it is smaller, immutable and exactly what the next caller needs.

Keeping the Cache True

Every cache answers one question: how stale may this data be? A TTL gives an upper bound; eviction on change makes the common case fresh. They complement each other — the TTL catches every change that bypassed the eviction, such as a SQL fix run directly against the database.

StrategyHowStaleness
TTL onlytime-to-liveUp to the TTL after every change
Evict on write + TTL@CacheEvict where the data changesNear zero for changes made through the service; TTL as a safety net
Evict on eventAnother service publishes ProductUpdated; the cache owner evictsThe event's delivery delay — the option when the change happens in a different service
Evict after the database commits

@CacheEvict runs when the method returns — which, inside a @Transactional method, is before the transaction commits. A read on another replica in that gap misses the cache, loads the old row from the database and caches it again for the full TTL. Make the evicting method the transaction boundary's caller, or evict from a listener that runs after commit (@TransactionalEventListener), or let Spring's transaction-aware cache decorator delay the eviction until commit.

What to Cache — and What Never to Cache

DataCache it?Why
Product details, categoriesYesRead constantly, changed rarely, a few seconds of staleness is harmless
PricesFor display, with a short TTLCheckout recalculates from the database — the charged price never comes from the cache
Stock levelsNoCorrectness depends on the current value; a cached "3 in stock" sells items that are gone
Per-customer data (cart, addresses)RarelyLow reuse; keys must include the customer, or one customer sees another's data

Two failure modes to design for: a stampede, when a popular entry expires and hundreds of requests reload it at once (@Cacheable(sync = true) lets only one load per instance), and Redis itself being unavailable — the shop should fall back to the database, slower, rather than fail, which a custom CacheErrorHandler can arrange.

Best Practices and Common Pitfalls

✅ Do

  • Measure first: cache where reads are frequent, data changes rarely and the load is real
  • Give every cache a TTL that matches how stale its data may be
  • Store values as JSON and cache response records, not entities
  • Evict where the data changes, after the transaction commits
  • Build keys from every input that changes the result (sku, locale, currency)
  • Monitor the hit ratio; a cache with a low hit ratio is only extra latency and memory

❌ Don't

  • Don't cache data whose correctness depends on freshness — stock, balances, payment state
  • Don't use per-instance maps as a cache for data that several replicas serve
  • Don't rely on Java serialization for cached values
  • Don't call a @Cacheable method from the same class — the proxy is bypassed and nothing is cached
  • Don't let a Redis outage take the shop down with it

Interview Questions

🎓 Junior level
What do @Cacheable and @CacheEvict do?

@Cacheable returns the cached result for the method's key when there is one and only runs the method on a miss, storing its result. @CacheEvict removes an entry, usually from the method that changes the underlying data, so the next read loads the new version.

Why use Redis instead of an in-memory map when the application has several replicas?

Each replica's map is separate: an eviction on one leaves the others serving stale data, and each fills its own memory. Redis is one shared cache that every replica reads and evicts, with expiry and memory limits built in.

What is a TTL, and why should every cache have one?

Time to live: how long an entry is kept before it expires. It bounds how stale cached data can get even when an eviction is missed, and stops the cache from keeping entries that nobody reads any more.

🔥 Senior level
Why can @CacheEvict on a @Transactional method leave stale data in the cache?

The eviction happens when the method returns, before the transaction commits. A concurrent read in between misses the cache, reads the old committed row and caches it again for the full TTL. Evicting after commit — from a transactional event listener, a transaction-aware cache, or a caller outside the transaction — closes the gap.

What is a cache stampede, and how do you prevent it?

When a popular entry expires, many concurrent requests miss at once and all hit the database to rebuild it. Mitigations: @Cacheable(sync = true) so one request per instance loads while the others wait, randomised TTLs so entries don't expire together, and refreshing hot entries before they expire.

Why is the default Java serialization a poor choice for a Redis cache?

It forces cached classes to be Serializable, breaks when a class changes between deployments so the new version cannot read the old entries, is opaque when inspecting Redis, and Java deserialization of data an attacker can influence is a known remote-code-execution vector. JSON with explicit types avoids all of these.

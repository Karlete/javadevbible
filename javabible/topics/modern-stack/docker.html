Docker for Spring Boot

From a fat JAR copied into an image to a layered build that rebuilds in seconds — plus the JVM memory and shutdown settings that containers get wrong, and a Compose file that runs Postgres and Kafka next to the shop on every machine

What a Container Image Is — and Why "It Works on My Machine" Stops Being an Excuse

A Spring Boot JAR is not self-contained. It needs a specific Java runtime, the right operating-system libraries, environment variables, and — for the shop — a PostgreSQL database and a Kafka broker. Every machine that runs it has to provide all of that, and every machine provides it slightly differently.

A container image packages the application together with the runtime and the filesystem it expects: a read-only stack of layers, each one the result of an instruction in a Dockerfile. A container is a running process started from an image, isolated by the Linux kernel (namespaces for what it can see, cgroups for how much CPU and memory it can use). The same image runs on a laptop, in CI and in production, so the difference between environments shrinks to configuration.

Writing a Dockerfile that works takes three lines. Writing one that builds fast, starts fast, shuts down cleanly and respects memory limits is where the actual skill is:

Layers and the Build Cache — Why Order Matters

Every instruction that changes the filesystem (COPY, RUN, ADD) produces a layer, identified by a hash of its content. Docker reuses a cached layer only if that instruction and every instruction before it are unchanged. The moment one layer changes, every layer after it is rebuilt — and every registry push and server pull transfers only the layers the other side does not have.

That makes the order of COPY instructions a performance decision. Spring Boot's tools mode (-Djarmode=tools, the replacement for the older layertools mode) splits the fat JAR into four directories so they can become four layers:

LayerContentsChanges when
dependenciesRelease JARs: Spring, Hibernate, the Kafka client…You upgrade a library — a few times a month
spring-boot-loaderThe launcher that boots the extracted layoutYou upgrade Spring Boot
snapshot-dependencies-SNAPSHOT JARs, e.g. an internal library under developmentOften, during development
applicationYour classes and application.yamlEvery commit

With this order, a commit that touches only OrderService rebuilds and ships a layer of a few hundred kilobytes; the dependency layer stays cached on the CI runner, in the registry and on every node that already pulled the previous version.

The extracted layout also starts faster

The runtime stage does not run the fat JAR. It runs an application.jar that contains only your code and references the extracted dependency JARs on the filesystem. Loading classes from plain files is faster than unpacking nested JARs, and it is the layout the AOT cache and CDS require — a cache trained against the fat JAR has no effect.

Faster Startup: the AOT Cache on Java 25

A Spring Boot application spends most of its startup loading, linking and initialising thousands of classes. The JVM can record that work during a training run and store it in an AOT cache file; the next start maps the cache instead of repeating the work. Spring Boot supports the AOT cache from Java 25 on; on older Java versions the equivalent, with a smaller gain, is Class Data Sharing (CDS).

The training run executes during docker build, and it refreshes the whole application context. In the shop that means Flyway wants to migrate a database and Hibernate wants to read JDBC metadata — and there is no database inside a build. The cache is tied to one build

An AOT cache is valid only for the exact application and the exact JVM that produced it. Train it in the same Dockerfile, on the same base image, as the image that uses it — never copy an app.aot between builds. And measure: the gain depends on how much of startup is class loading versus, for example, waiting for a connection pool.

No Dockerfile at All: Cloud Native Buildpacks

The Spring Boot Maven and Gradle plugins can build an OCI image without a Dockerfile, using Paketo buildpacks. The plugin detects the Java version from the build, picks a matching JRE, applies the same layering and produces a non-root image:

The JVM Inside a Container: Memory and Shutdown

Memory: the default heap is a quarter of the limit

The JVM is container-aware: it reads the cgroup memory limit, not the host's RAM. But its default maximum heap is 25% of that limit. A shop container limited to 2 GiB gets a 512 MiB heap and leaves 1.5 GiB unused — or, if someone "fixes" it with -Xmx2g, the heap plus metaspace, thread stacks and direct buffers exceed the limit and the kernel kills the container (exit code 137, OOMKilled) with no OutOfMemoryError in the logs.

Shutdown: two timeouts that must agree

docker stop sends SIGTERM, waits (10 seconds by default) and then sends SIGKILL. Since Spring Boot 3.4, graceful shutdown is on by default: on SIGTERM the embedded server stops accepting requests and lets in-flight ones finish, for up to spring.lifecycle.timeout-per-shutdown-phase (30 seconds by default). If Docker's grace period is shorter than Spring's, Docker wins: a checkout halfway through OrderService.placeOrder() is killed mid-request.

None of this works with a shell-form ENTRYPOINT: the signal goes to /bin/sh, Java never sees it, and the container always dies by SIGKILL after the grace period.

Docker Compose: Postgres and Kafka on Every Developer's Machine

The shop needs PostgreSQL for orders and Kafka for the OrderPlaced events the notification module consumes. Installing both on every laptop, at the right versions, is the classic onboarding day lost. A compose.yaml in the repository describes them once:

Add the spring-boot-docker-compose module and Spring Boot does the rest at startup: it runs docker compose up, waits for the containers to be ready, and creates service connections from them — the JDBC URL with the randomly mapped port, the username and password, the Kafka bootstrap servers. There is no spring.datasource.url to keep in sync with the compose file.

Compose support is for development, not for tests or production

It is skipped in tests by default, and it does nothing in the packaged JAR because the module is optional. For integration tests, Testcontainers starts disposable containers per test run with the same service-connection mechanism; in production, the platform (Kubernetes, a managed database, a managed Kafka) provides the services and configuration comes from the environment.

Best Practices and Common Pitfalls

✅ Do

  • Extract the JAR with -Djarmode=tools … extract --layers and copy the layers from least to most volatile
  • Pin the base image to a major version (eclipse-temurin:25-jre), and rebuild regularly to pick up its security patches
  • Use a JRE in the runtime stage and run as a non-root user with a fixed UID
  • Use the exec form of ENTRYPOINT so the JVM receives SIGTERM
  • Size the heap with -XX:MaxRAMPercentage so it follows the container limit
  • Make the orchestrator's grace period longer than spring.lifecycle.timeout-per-shutdown-phase
  • Keep a .dockerignore (target/ except the JAR, .git, IDE folders) so the build context stays small
  • Inject configuration and secrets through environment variables or the platform's secret store at run time

❌ Don't

  • Don't copy the fat JAR as a single layer — every deploy re-ships all dependencies
  • Don't use latest or the deprecated openjdk image
  • Don't hard-code -Xmx equal to the container limit — non-heap memory pushes the container over and it gets OOMKilled without a Java error
  • Don't bake passwords, API keys or application-prod.yaml secrets into the image: every layer is readable by anyone who can pull it
  • Don't build the JAR inside the runtime image with Maven — build it in CI (or a builder stage) and ship only the result
  • Don't reuse an AOT cache or CDS archive across builds or JVM versions

Interview Questions

🎓 Junior level
What is the difference between an image and a container?

An image is a read-only, layered filesystem plus metadata (the entrypoint, environment, exposed ports). A container is a running process started from an image, with a thin writable layer on top and its own isolated view of processes, network and filesystem. One image can run as many containers at once — three replicas of the shop are three containers from the same image.

Why copy dependencies and application code in separate layers?

Docker caches layers and reuses a layer only if it and every layer before it are unchanged. Dependencies change rarely and are large; application code changes on every commit and is small. Copying dependencies first means a code change rebuilds and transfers only the small application layer instead of the whole fat JAR.

What does a multi-stage build give you?

A builder stage can contain tools needed only to produce the artifact — here, extracting the JAR; in other setups, Maven and a JDK — and the final stage copies only the result. The runtime image stays small and contains nothing an attacker could use to compile or download code.

How does the shop application find the database started by Docker Compose?

With spring-boot-docker-compose on the classpath, Spring Boot starts the services in compose.yaml, recognises them by image name or by the org.springframework.boot.service-connection label, and creates connection details from the running containers, including the host port Docker mapped. No spring.datasource.url is needed for local development.

🔥 Senior level
A Spring Boot container in production restarts with exit code 137 and there is no OutOfMemoryError in the logs. What happened and how do you fix it?

137 is 128 + 9: the process received SIGKILL, and with no stop request in progress that is the kernel's OOM killer enforcing the cgroup memory limit. The JVM never threw because the heap was not full — the process exceeded the limit: heap plus metaspace, thread stacks (hundreds of request threads), direct buffers (Netty, the Kafka client), code cache and GC overhead. The usual cause is -Xmx set close to the limit. Fix: size the heap as a percentage (-XX:MaxRAMPercentage=70–75), measure non-heap usage with Native Memory Tracking, cap what grows unbounded (thread pools, direct memory), and only then raise the limit if the measurements justify it.

Deployments drop a few checkout requests every time a pod or container is replaced, even with graceful shutdown enabled. Where do you look?

First the entrypoint: in shell form, /bin/sh is PID 1 and swallows SIGTERM, so the JVM is always SIGKILLed after the grace period. Second, the two timeouts: if the orchestrator's grace period (10s in Docker, 30s in Kubernetes) is not longer than spring.lifecycle.timeout-per-shutdown-phase, long requests are killed. Third, traffic routing: the load balancer may keep sending requests for a moment after SIGTERM; readiness must flip to "not ready" first — Spring Boot does this on shutdown, and in Kubernetes a short preStop sleep covers the window before endpoints are updated.

Buildpacks or a hand-written Dockerfile — how do you decide?

Buildpacks give a secure, layered, non-root image with no file to maintain, and a rebuild picks up patched JREs and OS packages — the right default for teams without platform conventions. A Dockerfile wins when you need control: a mandated base image, an extra OS package, a custom entrypoint, an AOT training run with a specific profile, or builds without access to the builder images. Either way the important properties are the same: layering, a JRE, non-root, exec-form entrypoint, pinned versions.

The AOT cache made startup faster locally but makes no difference in the deployed image. What could be wrong?

The cache is valid only for the same application and the same JVM that recorded it, and only when the application runs from the extracted layout. Common causes: the cache was trained against the fat JAR or on a different base image; it was copied from another build; the runtime entrypoint does not pass -XX:AOTCache; or the runtime image uses a different JDK build than the training stage. Train inside the same Dockerfile, on the same base image, against the extracted application.jar.

React Frontend for a Spring Boot API

What a Java developer needs to know to put a React client in front of the shop's /api/orders: components and state, types that match the records, server data without hand-written loading flags, errors that are ProblemDetail, and the proxy, CSRF and deployment details where frontend and backend meet

Checked against React 19.3 · Vite 8 · Spring Boot 4.2 — November 2026

What React Is — and the Problem It Solves for an API Like the Shop's

React is a JavaScript library for building user interfaces out of components: functions that take data and return a description of what the screen should show. When the data changes, React calls the function again and updates only the parts of the page that differ. You never write "find this element and change its text" — you write what the page looks like for a given state.

The problem that replaces is the one every page built by hand with fetch and the DOM runs into: the screen and the data drift apart. Every place that changes the data has to remember every element that shows it, plus the loading and error states nobody wrote.

The <ul> inside the function is JSX: syntax that the build turns into function calls. It looks like HTML, but it is TypeScript — {orders.map(…)} is an expression, and the compiler checks that order.status exists.

The Project: Vite, TypeScript, and Where It Lives

A React app is built by a separate toolchain. Vite is the common default: a dev server with instant reload, and a production build that writes static files — index.html, JavaScript and CSS — to dist/. Those files are all the browser needs; there is no Node.js process in production.

Types That Match the Records — and the Money Trap

The API's response records are the contract. On the TypeScript side they become types; nothing at runtime checks that they agree, so they are best generated from the API's OpenAPI description rather than written by hand. Whichever way, two Java types need a decision.

A BigDecimal sent as a JSON number becomes a double in the browser

By default Jackson writes BigDecimal as a JSON number, and every JavaScript number is a 64-bit float: 0.1 + 0.2 is 0.30000000000000004, and trailing zeros disappear (129.90 arrives as 129.9). For money, send a string and let the server do the arithmetic — the client only formats it with Intl.NumberFormat. A Long id above 253 has the same problem; the shop's ids are nowhere near it, but snowflake-style ids are.

Server Data: Queries, Mutations and ProblemDetail Errors

Loading, caching, retrying and refreshing server data is the part of a frontend most often written badly by hand. TanStack Query does it once: a query reads data under a key, a mutation changes it and tells the cache which keys are now stale.

A rejected order — out of stock, a validation error — arrives as a 409 or 400 with a ProblemDetail body, so the form can show problem.detail next to the button instead of a generic "something went wrong". The server decides the message; the client only displays it.

Local Development: the Vite Proxy Instead of CORS

During development Vite serves the frontend on port 5173 and Spring Boot runs on 8080 — two origins, so every fetch('/api/orders') would be a cross-origin request and need CORS. The simpler fix is to make it same-origin: Vite forwards /api to Spring Boot, and the browser only ever talks to 5173.

In production the same rule applies: serve the frontend and the API from one origin — the same Spring Boot application, or one Ingress routing /api to the backend and everything else to the static files — and CORS never comes up. CORS is for when the frontend genuinely lives on another domain.

Logging In: Session Cookies and CSRF

For a browser frontend on the same origin, the safest default is the one Spring Security already uses for server-rendered pages: an HttpOnly session cookie that JavaScript cannot read, so an XSS bug cannot steal it. Because the browser sends that cookie automatically, the API also needs CSRF protection — and a single-page app reads the CSRF token from a cookie and echoes it in a header.

Tokens in the browser still have their place — a third-party API, a frontend on another domain — but then the usual answer is a backend-for-frontend: a server-side component holds the OAuth tokens and the browser keeps only a session cookie. See JWT and OAuth 2.0.

Shipping the Build with the Backend

The simplest deployment puts the frontend inside the Spring Boot JAR: Vite builds into src/main/resources/static (or the build copies dist/ there), and Spring Boot serves those files like any other static resource. One artifact, one origin, one version.

Larger teams often deploy the frontend separately — static files on a CDN, released on their own schedule. That trades the single artifact for independent releases, and brings back the cross-origin questions from the previous sections.

Best Practices and Common Pitfalls

✅ Do

  • Generate the TypeScript types from the API's OpenAPI description, so the compiler catches a renamed field
  • Send money as a decimal string and keep the arithmetic on the server
  • Use one fetch wrapper that checks response.ok and turns problem details into a typed error
  • Use a server-state library (TanStack Query) for loading, caching and invalidation instead of hand-written flags
  • Proxy /api to Spring Boot in development and serve frontend and API from one origin in production
  • Keep authentication in an HttpOnly cookie and enable CSRF protection with csrf.spa()
  • Validate everything again on the server — the browser only gives early feedback

❌ Don't

  • Don't store access tokens in localStorage
  • Don't build HTML strings from API data with innerHTML — or bypass React's escaping with dangerouslySetInnerHTML
  • Don't disable CSRF because "it's an API" when the browser authenticates with a cookie
  • Don't configure CORS with * to make local development work — use the dev proxy
  • Don't compute prices, discounts or totals in the browser and trust them on the server
  • Don't forward every unknown path to index.html, including /api/** — clients then get HTML where they expect JSON

Interview Questions

🎓 Junior level
What is a React component, and what makes it re-render?

A component is a function that returns a description of the UI (JSX) for its props and state. React calls it again when its state changes, its parent re-renders, or a context it reads changes, and then updates only the parts of the real DOM that differ from the previous result.

Why does the frontend need to check response.ok when calling the shop API?

Because fetch() only rejects on network failures. A 400, 404 or 500 is a successful fetch with an error status; without the check, the code tries to read an error body as if it were the expected data.

How does the Vite dev proxy avoid CORS during development?

The browser sends every request to the Vite dev server's own origin, and Vite forwards /api requests to Spring Boot server-side. From the browser's point of view nothing is cross-origin, so no CORS headers are needed.

What happens when a user reloads the page on a client-side route like /orders/42?

The browser requests /orders/42 from the server, which has no file or controller for it. Unless the server forwards such paths to index.html, the user gets a 404; with the forward, React loads and its router renders the order page.

🔥 Senior level
Why should a BigDecimal amount be serialised as a string for a JavaScript client?

JavaScript has one number type, a 64-bit binary float, so decimal values lose exactness and formatting (129.90 becomes 129.9; sums drift by fractions of a cent). Sending the amount as a string keeps the exact value, and the client only formats it. The same applies to 64-bit ids above 253.

A team stores a JWT in localStorage for their React app. What would you change, and why?

Anything running in the page can read localStorage, so one XSS bug or a malicious dependency can exfiltrate the token, and a bearer token cannot be tied to the browser it was issued to. For a same-origin frontend, an HttpOnly session cookie plus CSRF protection is safer. If OAuth tokens are needed, keep them in a backend-for-frontend and give the browser only a session cookie.

Why does an SPA authenticated by cookies still need CSRF protection, and how does csrf.spa() provide it?

The browser attaches the session cookie to any request to the shop's domain, including one triggered by a form on another site. CSRF protection requires a value the other site cannot read: Spring Security puts the token in a cookie readable only by scripts on the shop's own origin, and rejects state-changing requests that don't echo it in the X-XSRF-TOKEN header. csrf.spa() configures that cookie repository and the matching request handler in one call.

When would you deploy the frontend separately from the Spring Boot application instead of inside the JAR?

When the frontend and backend teams need independent release cycles, when the static files should come from a CDN close to users, or when several backends serve one frontend. The cost is a second deployment pipeline, version compatibility between the two, and — if the origins differ — CORS and cookie configuration that a single origin avoids.

How do you keep the TypeScript types and the Java records from drifting apart?

Generate one from the other. Spring Boot can publish an OpenAPI document describing the records (springdoc), and a generator produces the TypeScript types and even the fetch functions in the frontend build. A renamed field then fails the TypeScript compile instead of rendering undefined in production.

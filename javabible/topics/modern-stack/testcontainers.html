Testcontainers with Spring Boot

Testing the shop against the PostgreSQL and Kafka it runs on in production, started in Docker by the test itself — why H2 gives false confidence, how Spring Boot wires a container in one annotation, and how to keep the suite fast

What Testcontainers Is — and Why H2 Is the Wrong Database to Test Against

Testcontainers is a Java library that starts real services — PostgreSQL, Kafka, Redis — in Docker containers for the duration of a test, and removes them afterwards. The test talks to the same database engine, the same version, that production uses.

The usual alternative is an in-memory database such as H2. It is fast and needs nothing installed, but it is a different database: its SQL dialect, its locking, its types and its error codes are not PostgreSQL's. Tests pass against H2 and the code fails in production — or tests fail on H2 for code that is correct on PostgreSQL, and someone "fixes" the code to please the test database.

How It Works, and What It Costs

Testcontainers talks to the local Docker daemon (or any compatible runtime: Podman, Colima, a remote Docker host). It pulls the image once, starts the container on a random free port, waits until the service inside is actually ready — not just started — and exposes the mapped host and port to the test. A small companion container removes everything when the test JVM exits, even if it crashes.

One Set of Containers for the Whole Suite

A static @Container field starts a container per test class. With fifty integration test classes, that is fifty PostgreSQL startups. The faster pattern declares the containers once as beans in a test configuration: every test that imports it shares the same Spring context — which Spring's test framework caches — and therefore the same containers.

@DirtiesContext and differing configurations defeat the sharing

The containers live as long as the cached context. A test class that adds @DirtiesContext, a different @MockitoBean set or different properties gets a new context — and a new set of containers. Keep integration tests on a small number of identical configurations, and clean up data between tests (a transaction rolled back, or tables truncated) instead of throwing the context away.

Testing the Order Flow Through Kafka

The checkout publishes OrderPlacedEvent and the notification module consumes it — the flow from the Kafka page. With real Kafka the test exercises serialisation, topic configuration and the listener together. Because consumption is asynchronous, the assertion waits until the effect is visible instead of sleeping.

Running the Application Locally on the Same Containers

The test configuration can also start the whole application for local development: a small main class in the test sources runs ShopApplication with the containers attached. It replaces the Compose file for developers who only need the application's own dependencies.

Best Practices and Common Pitfalls

✅ Do

  • Use the same image and major version in tests as in production (postgres:19, apache/kafka:4.4.0), pinned, never latest
  • Let @ServiceConnection wire the connection instead of copying URLs into @DynamicPropertySource
  • Share containers across the suite through one test configuration and Spring's context cache
  • Run the real schema migrations against the container
  • Wait for asynchronous effects with Awaitility, with a timeout
  • Keep unit tests without containers; use Testcontainers where the database, broker or wire format is part of what is being tested

❌ Don't

  • Don't use H2 to stand in for PostgreSQL in tests of SQL, migrations or locking
  • Don't Thread.sleep() to wait for a Kafka consumer
  • Don't add @DirtiesContext to clean data — it restarts the containers
  • Don't rely on test execution order or on data left behind by another test
  • Don't hard-code ports; containers get a random free port

Interview Questions

🎓 Junior level
What does Testcontainers do?

It starts real services such as PostgreSQL or Kafka in Docker containers for a test, waits until they are ready, gives the test their host and port, and removes them afterwards, so integration tests run against the same software as production.

Why is H2 a poor substitute for PostgreSQL in tests?

It is a different database: SQL features such as ON CONFLICT, types such as jsonb, locking behaviour and error codes differ. Tests can pass on H2 while the code fails on PostgreSQL, or force changes to correct code just to satisfy H2.

What does @ServiceConnection do?

It tells Spring Boot to create the connection details for a service from a container — the JDBC URL, user and password for PostgreSQL, the bootstrap servers for Kafka — so the application connects to the container without any properties being set by hand.

🔥 Senior level
An integration test suite with Testcontainers takes fifteen minutes. Where would you look first?

At how many times the containers and the Spring context start. Containers declared per test class, @DirtiesContext, and many slightly different test configurations each force new contexts and new containers. Declaring the containers once in a shared test configuration and keeping test classes on identical configurations usually cuts the time to a single startup; after that, check whether some tests could be plain unit tests.

How do you test asynchronous processing, such as a Kafka consumer, without flaky tests?

Trigger the action, then poll for the expected effect with a bounded timeout — Awaitility's await().atMost(…).untilAsserted(…) — instead of sleeping for a fixed time. The test finishes as soon as the effect is visible, and fails with a meaningful assertion if it never appears. Assert on an observable outcome (a database row, a mock interaction), not on internal timing.

Which tests should use Testcontainers, and which should not?

Use it where the external system is part of what is being verified: repository queries, migrations, transaction and locking behaviour, message serialisation and listener configuration, end-to-end flows. Keep business logic in fast unit tests with plain objects or mocks; running every test against a database makes the suite slow without making it more meaningful.

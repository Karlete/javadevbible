What OpenAPI Is — and Why Hand-Written API Docs Drift

OpenAPI is a standard format, in JSON or YAML, for describing an HTTP API: every path and method, its parameters, request and response bodies with their exact fields and types, the status codes it returns and how it is secured. Because it is machine-readable, tools can render it as interactive documentation, generate client code from it, and compare two versions of it.

The problem it solves is the gap between an API and what its clients believe about it. A README or a wiki page describing the endpoints is out of date the first time someone adds a field and forgets to update it; a TypeScript type written by hand on the frontend drifts the same way, and nothing fails until a customer sees undefined on the screen.

springdoc: the Description From the Code

springdoc-openapi inspects the application at runtime — request mappings, parameter and return types, Jackson's view of the records, Bean Validation annotations — and serves the resulting OpenAPI document. Its 3.x line targets Spring Boot 4; Boot does not manage its version.

Making the Description Accurate

Out of the box the description is only as precise as the code. Three things usually need help: which fields are required, the error responses, and types whose JSON shape differs from their Java type.

Code-First or Contract-First

springdoc works code-first: the Java code is the source and the description is derived from it. The alternative writes the OpenAPI document first and generates server interfaces from it (for example with the openapi-generator Maven plugin), which the controllers then implement.

Code-first (springdoc)Contract-first (generator)
Source of truthControllers and recordsThe OpenAPI YAML file
StrengthNo duplication; the description cannot disagree with the codeFrontend and backend agree on the contract before implementation; reviewable as one file
WeaknessThe API's design emerges from implementation details unless reviewedGenerated code to live with; generator quirks; two artefacts to keep in step
FitsOne team owning API and main client — the shopPublic APIs, several teams or companies consuming one contract

Generated Clients for the React and Angular Frontends

The React and Angular pages wrote the TypeScript types by hand and noted that they should be generated. openapi-typescript turns the description into types for every path; openapi-fetch is a small fetch wrapper that uses them, so the path, its parameters and the response type are all checked by the compiler.

Java callers have the same choice: openapi-generator can produce a Java client, but for service-to-service calls inside one organisation the declarative @HttpExchange interfaces from the microservices page are usually lighter.

Catching Breaking Changes in CI

Once the description is a file, two versions of it can be compared. A CI step exports the document from the new build — from a test that calls /v3/api-docs and writes it to disk, for instance — and compares it with the one from the main branch using a diff tool such as oasdiff. Removing a field, renaming a path or making an optional parameter required fails the build; adding an optional field passes.

ChangeBreaking for existing clients?
Add an optional request field or a response fieldNo
Add an endpointNo
Remove or rename a response fieldYes — clients reading it get nothing
Make a request field requiredYes — existing requests are rejected
Add a value to a response enum (OrderStatus)Often — clients with an exhaustive switch fail on the new value

Best Practices and Common Pitfalls

✅ Do

  • Generate client types from the description instead of writing them by hand
  • Document error responses as application/problem+json with the ProblemDetail schema
  • Use Bean Validation annotations on request records so constraints appear in the description
  • Make the schema match Jackson's output for types with a custom shape, such as money as strings
  • Compare the description against the previous release in CI and fail on breaking changes
  • Review API changes in the description diff, not only in the Java diff

❌ Don't

  • Don't expose Swagger UI publicly in production
  • Don't return JPA entities from controllers — the description then publishes your database model
  • Don't edit generated code; change the source and regenerate
  • Don't treat the generated description as API design: review names, paths and status codes deliberately

Interview Questions

🎓 Junior level
What is an OpenAPI document?

A machine-readable description of an HTTP API in JSON or YAML: its paths, methods, parameters, request and response schemas, status codes and security schemes. Tools use it to render documentation, generate clients and compare versions.

What does springdoc do in a Spring Boot application?

It inspects the controllers, their parameter and return types and the validation annotations at runtime and serves the resulting OpenAPI document at /v3/api-docs, plus an optional Swagger UI that renders it.

Why generate frontend types from the API description?

So they cannot drift from the backend: when a field is renamed or removed, the regenerated types change and the frontend fails to compile, instead of silently showing missing data to users.

🔥 Senior level
Code-first or contract-first — how do you choose?

Code-first suits one team owning the API and its main client: the description is derived and cannot disagree with the code. Contract-first suits public APIs and several consuming teams, where the contract is agreed and reviewed before implementation and generated server interfaces enforce it. The cost is generated code and keeping the contract and implementation in step.

Which API changes are breaking, and how do you catch them before release?

Removing or renaming response fields, removing endpoints, adding required request fields, changing types, and often adding enum values that clients handle exhaustively. Export the OpenAPI document in CI and diff it against the released version with a tool such as oasdiff, failing the build on breaking changes unless a new API version is introduced.

The shop's total is a BigDecimal written as a JSON string. What can go wrong in the OpenAPI description, and how do you fix it?

The generator sees a BigDecimal and documents a number, while Jackson actually sends a string, so generated clients get the wrong type and may parse it as a float. Annotate the component with @Schema(type = "string") so the description matches the wire format, and verify with a test that compares an actual response to the schema.

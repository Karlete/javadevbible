Database Migrations: Flyway and Liquibase

What a Database Migration Is — and Why Hibernate Shouldn't Write Your Schema

A migration is one versioned change to the database schema — a new table, a new column, an index — stored as a file in the codebase. A migration tool such as Flyway applies the files in version order and records which ones each database has already run, so every environment, from a developer's laptop to production, reaches the same schema by the same steps.

The problem it replaces is schema drift: SQL scripts run by hand and forgotten on one environment, or Hibernate creating and altering tables on startup. The latter looks convenient and is how many projects start.

How Flyway Works

On startup, before JPA initialises, Spring Boot runs Flyway against the application's DataSource. Flyway reads the flyway_schema_history table, compares it with the files in classpath:db/migration, and applies the missing ones in version order — each in its own transaction on PostgreSQL, so a failing migration leaves no half-applied change.

FileMeaning
V3__create_stock_levels.sqlVersioned: runs exactly once, in version order. Never edited after it has run anywhere
V3_1__backfill_stock_levels.sqlVersions can have parts: 3.1 runs after 3 and before 4
R__order_summary_view.sqlRepeatable: re-runs whenever its content changes — for views and functions that are replaced as a whole
An applied migration is immutable

Flyway stores a checksum of every migration it ran. Edit V3__create_stock_levels.sql after it reached any shared environment and the next startup fails validation, because that database was built from the old version. A mistake in an applied migration is fixed by a new migration, V5__fix_stock_levels_default.sql.

The Shop's Schema as Migrations

Migrations are plain SQL for the database you run, which means they can use everything PostgreSQL offers — constraints, partial indexes, CHECKs — that an ORM-generated schema leaves out.

Changing the Schema Without Downtime: Expand and Contract

During a rolling update the old and the new version of the shop run at the same time against the same database. The migration runs when the first new Pod starts, so for several minutes the old code is using the new schema. Every migration therefore has to be compatible with the version before it — which rules out renaming or dropping anything the old code still uses.

Watch the locks, not only the syntax

Some statements lock the whole table while they run. On a large orders table, a plain CREATE INDEX blocks writes — checkout — until it finishes; CREATE INDEX CONCURRENTLY does not, but cannot run inside a transaction, so that migration has to be configured to run outside one. Backfilling millions of rows in one UPDATE holds locks and bloats the table; do it in batches. The SQL page covers which DDL is safe online.

Where Migrations Run in Production

ApproachHowTrade-off
On application startupSpring Boot's defaultSimplest; Flyway takes a database lock so replicas starting together apply each migration once. A long migration delays startup — give the startup probe enough time
As a separate stepA Kubernetes Job or a CI step runs the migrations, then the rollout starts; the app sets spring.flyway.enabled=falseMigrations run once, with their own timeout and logs, and a failure stops the deployment before any Pod changes

Either way, the database user the application runs with in production does not need permission to create or drop tables if a separate, more privileged user applies the migrations.

Testing Migrations, and Where Liquibase Fits

Run the real migrations in tests, against the real database engine. With Testcontainers every integration test starts from an empty PostgreSQL and applies V1 to the latest — the same path a new environment takes — and ddl-auto: validate fails the test if an entity and the schema disagree.

Best Practices and Common Pitfalls

✅ Do

  • Keep the schema in versioned migrations and set ddl-auto: validate
  • Make every migration compatible with the previous application version; rename and drop with expand and contract
  • Fix mistakes with a new migration, never by editing an applied one
  • Review migrations like code, including the locks they take on large tables
  • Test migrations against the production engine and a realistic amount of data before release
  • Back up before migrations that move or delete data

❌ Don't

  • Don't use ddl-auto: update or create outside throwaway prototypes
  • Don't rename or drop a column in the same release that stops using it
  • Don't edit or delete a migration that has run on a shared database
  • Don't enable flyway clean anywhere near production — it drops every object in the schema
  • Don't run a migration that rewrites a huge table in one transaction during peak traffic

Interview Questions

🎓 Junior level
What does Flyway do when a Spring Boot application starts?

It reads the flyway_schema_history table, finds the migration files in db/migration that have not run yet, and applies them in version order before JPA starts, recording each one in the history table.

Why is ddl-auto=update a bad idea in production?

Hibernate only adds what is missing: it does not rename or drop columns, cannot migrate data, leaves no reviewable record of changes, and several instances may try to alter tables at the same time. Versioned migrations with validate give control and history instead.

What happens if you edit a migration that has already been applied?

Flyway detects that its checksum no longer matches the one recorded in the history table and fails validation on startup. The correct fix is a new migration that changes the schema further.

🔥 Senior level
How do you rename a column without downtime in a service deployed with rolling updates?

With expand and contract over several releases: add the new column and write to both; backfill and switch reads to the new column; and only when no running version uses the old column, drop it. Each step stays compatible with the version deployed just before it, because both run side by side during a rollout.

Should migrations run on application startup or as a separate deployment step?

Startup is simplest and Flyway's lock keeps concurrent replicas safe, but a long migration delays readiness and its failure surfaces as crash-looping Pods. A separate job runs migrations once, with its own timeout and logs, blocks the rollout on failure, and allows a more privileged database user than the application's. Larger systems usually prefer the separate step.

Why can a migration that is correct SQL still cause an outage?

Because of locks and volume. Adding an index without CONCURRENTLY, rewriting a column type, or updating every row of a large table can lock it for minutes, blocking the application's writes. Such changes need online variants, batching, and testing against production-sized data.

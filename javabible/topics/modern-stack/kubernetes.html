Kubernetes for Spring Boot

The shop's image from the Docker page, running as three replicas that restart themselves, receive traffic only when ready, and roll out a new version without dropping a single checkout

What Kubernetes Is — and the Job It Takes Off Your Hands

Kubernetes is a container orchestrator: you describe the state you want — "three copies of shop:1.4.0, each with 1 GiB of memory, reachable on port 80" — and a control loop keeps the cluster in that state. If a container crashes, it is restarted; if a node dies, its containers are started on another node; if you change the image tag, the old copies are replaced by new ones a few at a time.

The problem it solves starts where the Docker page ends. An image runs the same everywhere, but someone still has to decide where it runs, restart it when it fails, spread traffic over several copies, and replace it without downtime. Without an orchestrator, that someone is a script:

The whole of Kubernetes is that idea applied to more things: networking, configuration, storage, scaling. This page covers the part an application developer has to get right — the parts where a Spring Boot service and the cluster have to cooperate.

The Five Objects a Spring Boot Service Needs

A cluster has dozens of resource types. A typical stateless service uses five of them; the database and Kafka usually run as managed services outside the cluster, or are operated by a platform team.

ObjectWhat it isFor the shop
PodOne or more containers scheduled together, with one IP address. Disposable: it is never repaired, only replacedOne running copy of shop:1.4.0
DeploymentKeeps N identical Pods running and replaces them on every change to the Pod templateThree replicas, rolled out one at a time

Health Probes — Liveness, Readiness and Startup

Kubernetes asks each container three different questions, and confusing them is the most common cause of a service that restarts itself into an outage:

ProbeQuestionWhen it fails
StartupHas the application finished starting?The other probes wait; after failureThreshold × periodSeconds the container is restarted
LivenessIs this process broken beyond repair?The container is killed and restarted
ReadinessShould this Pod receive requests right now?The Pod is removed from the Service; nothing is restarted

Spring Boot answers liveness and readiness out of the box. When it detects Kubernetes — from the *_SERVICE_HOST and *_SERVICE_PORT environment variables every Pod receives — Actuator enables two health groups, /actuator/health/liveness and /actuator/health/readiness, backed by the application's own availability state: live once the context has refreshed, ready once the startup runners have finished.

Code review comment

management.endpoint.health.group.liveness.include: livenessState,db
management.endpoint.health.group.readiness.include: readinessState,db

Please don't put the database in liveness. If Postgres has a two-minute failover, every replica fails liveness, Kubernetes restarts all of them, and they come back into a cold start while the database is recovering. Readiness takes them out of the load balancer instead and lets them return on their own.

Liveness must only check the process itself

A failing liveness probe restarts the container — so it should fail only when a restart would help: a deadlock, a broken internal state. A dependency that is down is not fixed by restarting the caller. The Spring Boot documentation is explicit that liveness should not depend on external checks. Whether readiness includes the database is a choice: with it, a Pod that has lost its connection pool stops receiving checkouts; without it, a database outage keeps every Pod "ready" and requests fail with 500s instead of being refused.

The probes run on the application port by default. If Actuator lives on a separate management port that a broken web server would not affect, management.endpoint.health.probes.add-additional-paths=true also exposes them as /livez and /readyz on the main port, so the probe tests the same server that serves customers.

Requests, Limits and the JVM

Each container declares what it needs. The scheduler uses requests to choose a node; the kernel enforces limits. For memory the limit is hard: a container that exceeds it is killed (OOMKilled, exit code 137) with no Java error and no heap dump. For CPU, the limit throttles: the JVM keeps running, just slower, which shows up as latency spikes during garbage collection and JIT compilation.

A small container can silently get the wrong garbage collector

On Java 25 the JVM only picks G1 on a "server-class" machine; a container with fewer than two CPUs or less than about 1.8 GB of memory gets the Serial collector, with its single-threaded pauses. Either give the container at least two CPUs or set -XX:+UseG1GC explicitly. Java 27 made G1 the default everywhere, which removes the trap for the next LTS.

Leaving out the CPU limit, as above, is a deliberate and common choice: the request still guarantees the Pod its share, and the JVM can use idle CPU on the node during startup and GC instead of being throttled. Teams that need strict isolation between workloads set a limit and size it generously.

Rolling Updates Without Dropping a Checkout

Changing the image tag starts a rolling update: new Pods are started, and old ones are terminated once the new ones are ready. Two things decide whether customers notice — how the Deployment replaces Pods, and how a terminating Pod leaves.

Termination is where requests get lost. When a Pod is deleted, two things happen at the same time: the container receives SIGTERM, and the Pod is removed from the Service's endpoints. The second one propagates to every node and Ingress controller asynchronously, so for a few seconds traffic still arrives at a Pod that is already shutting down. The sequence that avoids it:

StepWhat happensBudget
1. preStop hookThe container waits before receiving SIGTERM, while endpoint removal reaches every load balancer10 s
2. SIGTERM → graceful shutdownSpring Boot (graceful by default) stops accepting new requests and lets in-flight ones finishup to 30 s (spring.lifecycle.timeout-per-shutdown-phase)
3. terminationGracePeriodSecondsAfter this, Kubernetes sends SIGKILL — it must cover steps 1 and 245 s > 10 + 30

On clusters older than 1.32 the same delay is an exec hook running sh -c "sleep 10", which only works if the image has a shell. And none of it helps if the JVM never sees SIGTERM — the image needs the exec form of ENTRYPOINT described on the Docker page.

Configuration and Secrets

The same image runs in every environment; what changes is configuration, and Spring Boot already reads it from the two places Kubernetes can put it. Environment variables map to properties through relaxed binding (SPRING_DATASOURCE_URL → spring.datasource.url); files mounted from a Secret become properties through configtree:.

A Secret is base64, not encryption

Anyone who can read the Secret object can decode it, and by default it is stored unencrypted in the cluster's database. Restrict who can read Secrets, enable encryption at rest, and for production credentials prefer an external secret store synchronised into the cluster. Mounting secrets as files rather than environment variables also keeps them out of /actuator/env, crash reports and child processes.

Scaling the Shop Horizontally

A HorizontalPodAutoscaler changes replicas from a metric. CPU is the usual one; for a JVM it needs two adjustments to behave.

  • Startup looks like load. A new JVM burns CPU on class loading and JIT compilation, which can push the average up and trigger another scale-up. The startup probe keeps new Pods out of the metric until they are ready; the AOT cache from the Docker page shortens the window.
  • Kafka consumers don't scale past the partitions. The notification consumer group from the Kafka page can only have as many active consumers as orders.placed has partitions; replicas beyond that sit idle.

Best Practices and Common Pitfalls

✅ Do

  • Use Actuator's /actuator/health/liveness and /readiness groups for the probes, and add a startup probe for slow starts
  • Keep liveness limited to the process itself; put dependencies, if anywhere, in readiness
  • Set the memory request equal to the limit and size the heap with -XX:MaxRAMPercentage
  • Add a preStop sleep and make terminationGracePeriodSeconds longer than the sleep plus Spring's shutdown timeout
  • Use maxUnavailable: 0 for services that must not lose capacity during a rollout
  • Deploy by immutable image tag or digest, and keep the manifests in Git next to the code or in a GitOps repository
  • Mount credentials as files from Secrets and read them with configtree:

❌ Don't

  • Don't check the database, Kafka or another service in the liveness probe — an outage elsewhere turns into a restart storm
  • Don't use latest as the image tag: a restarted Pod may pull a different image than its siblings
  • Don't set -Xmx equal to the memory limit; non-heap memory gets the container OOMKilled
  • Don't run a single replica of a service that customers depend on — every node drain or rollout is then an outage
  • Don't treat Secrets as encrypted, and don't commit them to Git, even base64-encoded
  • Don't run more consumer replicas than the topic has partitions and expect more throughput

Interview Questions

🎓 Junior level
What is the difference between a Pod, a Deployment and a Service?

A Pod is one running instance: one or more containers with a shared IP, created and destroyed freely. A Deployment keeps a given number of identical Pods running and replaces them when their template changes. A Service gives those Pods one stable name and address and load-balances across the ones that are ready, so callers never deal with Pod IPs.

What happens when a liveness probe fails, and when a readiness probe fails?

A failing liveness probe gets the container killed and restarted. A failing readiness probe only removes the Pod from the Service's endpoints, so it stops receiving traffic until the probe passes again; nothing is restarted.

How does a Spring Boot application read configuration on Kubernetes?

The same way as anywhere else: from environment variables, which relaxed binding maps to properties (SPRING_DATASOURCE_URL → spring.datasource.url), and from files, which spring.config.import=configtree:/path/ turns into properties named after each file. ConfigMaps and Secrets provide both.

Why should a Spring Boot service run more than one replica?

Because Pods are replaced routinely — on every rollout, node upgrade or eviction. With one replica, each of those events is an outage; with several, the Service sends traffic to the others while one is being replaced.

🔥 Senior level
Why do some requests still fail during a rolling update even with graceful shutdown enabled?

Because SIGTERM and the removal of the Pod from the Service's endpoints happen in parallel, and endpoint removal reaches kube-proxy and the Ingress controllers asynchronously. For a few seconds new requests keep arriving at a Pod whose server has already stopped accepting them. A preStop sleep delays SIGTERM until the endpoint change has propagated, and terminationGracePeriodSeconds must cover the sleep plus Spring's shutdown timeout, or SIGKILL cuts the in-flight requests short.

Should the database be part of a health probe?

Never of liveness: when the database is down, every replica fails, Kubernetes restarts all of them, and the service comes back cold into an ongoing incident. In readiness it is a trade-off: it removes Pods that cannot serve requests, but during a full database outage it removes all of them, so the Service answers with connection errors instead of the application's own error responses. Many teams keep readiness to the application's own state and handle dependency failures with timeouts, circuit breakers and ProblemDetail errors.

A Spring Boot Pod is OOMKilled but the logs show no OutOfMemoryError. What is going on?

The container exceeded its memory limit and the kernel killed the process; the JVM never got to throw anything. The heap is only part of the process's memory — metaspace, thread stacks, the code cache, direct buffers and GC structures come on top. With -Xmx close to the limit, non-heap growth pushes the total over. Size the heap as a percentage of the limit (MaxRAMPercentage around 70–75), and use Native Memory Tracking to see what the rest is.

Why might a JVM service behave differently in a 1-CPU container than on a developer laptop?

Ergonomics. The JVM sizes thread pools, the heap and even its choice of garbage collector from the CPU and memory it sees, and it sees the container limits. On Java 25, under two CPUs or about 1.8 GB the JVM falls back to the Serial collector; common pools such as ForkJoinPool.commonPool() shrink to one thread; and a CPU limit throttles GC and JIT threads. Setting the collector explicitly and giving latency-sensitive services at least two CPUs avoids most of it — Java 27 makes G1 the default regardless of size.

Why doesn't adding replicas speed up a Kafka consumer beyond a certain point?

Within a consumer group, each partition is consumed by at most one member. With six partitions, the seventh replica gets no partition and sits idle. Throughput beyond that needs more partitions — planned up front, because adding partitions later changes which partition a key maps to and breaks per-key ordering for existing keys.

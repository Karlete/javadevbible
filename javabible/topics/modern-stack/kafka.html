Apache Kafka with Spring Boot

Publishing an OrderPlaced event instead of calling five services from the checkout — and the three things that make it reliable: keys for ordering, an outbox for the database-and-Kafka write, and consumers that survive duplicates

What Kafka Is — and Why the Checkout Should Not Call Everyone

When a customer places an order, several parts of the shop have to react: inventory reserves stock, invoicing creates an Invoice, notification sends a confirmation email, analytics records the sale. The obvious implementation calls each of them from OrderService. That makes the checkout as slow as the sum of all of them, and as fragile as the least reliable one: if the email provider is down, nobody can buy anything.

Apache Kafka is a distributed, durable, append-only log. Producers append records to a topic; consumers read them at their own pace and remember how far they got. Records are not deleted when they are read — they stay for the configured retention — so a new consumer can start from the beginning and a crashed one can resume where it stopped. The checkout publishes one fact, "this order was placed", and stops caring who listens.

Synchronous callsEvents through Kafka
Checkout latencySum of every downstream callOne database transaction
A downstream service is downThe checkout failsIts events wait in the topic until it is back
Adding a new reactionChange and redeploy the checkoutA new consumer group; the producer is untouched
CostSimple to follow and debugEventual consistency, duplicates to handle, a broker to run
Not everything should become an event

If the checkout cannot continue without the answer — "is the card authorised?" — that is a request, not an event, and a synchronous call with a timeout is the honest design. Events are for facts that other parts of the system react to afterwards.

Topics, Partitions, Offsets and Keys

Every Kafka question in an interview comes back to these five terms, and every production incident does too:

OffsetA record's position inside its partitionNotification has processed partition 3 up to offset 18 204
KeyRecords with the same key always go to the same partitionKey = order id: every event for one order stays in order

Two consequences follow directly. Ordering is guaranteed only inside a partition — so whatever must stay in order has to share a key. And a group cannot have more active consumers than the topic has partitions: with 12 partitions, a 13th notification instance sits idle. Choose the partition count for the parallelism you will need; adding partitions later changes which partition a key maps to.

Producing Events with KafkaTemplate

The event is a record: an immutable fact, named in the past tense, carrying what consumers need so they do not have to call back into the order module. The eventId lets consumers recognise a record they have already processed.

send() is asynchronous: it returns a CompletableFuture as soon as the record is in the producer's buffer. Ignoring the future means never learning that the broker rejected a record. With acks=all and idempotence (the defaults since Kafka 3.0), the producer retries transient failures without creating duplicates or reordering records within a partition.

The Dual-Write Problem and the Transactional Outbox

The checkout must do two things: commit the order to PostgreSQL and publish the event to Kafka. They are two systems, and no transaction spans both. Every naive ordering loses something:

ApproachFailureResult
Send inside the @Transactional methodThe transaction rolls back after the sendAn email for an order that does not exist
Send after commit (@TransactionalEventListener(AFTER_COMMIT))The process crashes, or Kafka is down, between commit and sendA paid order nobody invoices — silently
Transactional outboxAny crashThe event is retried until published; at worst it is published twice

The outbox turns two writes into one. The event is stored in an outbox_events table in the same transaction as the order; a relay publishes unpublished rows to Kafka and marks them as sent.

A crash after join() and before the commit publishes the same rows again on the next run. That is the trade the outbox makes: at-least-once delivery instead of lost events — which is exactly why consumers must be idempotent. In larger systems, change data capture (Debezium reading the outbox table from the PostgreSQL write-ahead log) replaces the polling relay with the same guarantees.

Consuming with @KafkaListener — and Surviving Duplicates

The notification module declares its own copy of the event. It depends on the shape of the message, not on the order module's classes, so the two can be deployed separately.

When is the offset committed?

By default the listener container commits offsets after the listener returns. If the instance dies after sending the email but before the commit, the next owner of the partition receives the record again. "Exactly once" between Kafka and an external side effect such as an email does not exist; an idempotent consumer is how you get effectively once.

Retries and Dead-Letter Topics

Without configuration, a failing record is retried in place (ten attempts in total) and then logged and skipped — the customer simply never gets the email. Production needs two decisions: how to retry, and where a record goes when retrying is pointless.

These retries are blocking: while one record waits for its back-off, the rest of its partition waits too. That preserves order and is fine for short retries. For long ones — the email provider is down for ten minutes — non-blocking retries move the record to retry topics and keep the main partition flowing, at the cost of ordering:

Blocking (DefaultErrorHandler)Non-blocking (@RetryableTopic)
Ordering within the partitionPreservedLost for retried records
Other records while one retriesWaitKeep flowing
FitsShort, transient failuresLong outages of a dependency, order-independent events

A DLT is only useful if someone reads it: alert on its growth and give operations a way to replay records once the cause is fixed.

Scaling Consumers and Rebalances

Each partition is consumed by exactly one member of a group. Scaling the notification module means more instances, or more listener threads per instance (spring.kafka.listener.concurrency), up to the partition count. When a member joins, leaves or stops polling, the group rebalances partitions between the remaining members.

The most common cause of mysterious rebalances is a listener that takes longer than max.poll.interval.ms (five minutes by default) to process one batch: the broker assumes the consumer is dead, reassigns its partitions, and the batch is processed again by someone else. Reduce max.poll.records or move slow work out of the listener.

Kafka 4 and the new consumer group protocol

Kafka 4.0 made the consumer rebalance protocol of KIP-848 generally available: the broker coordinates assignments incrementally, so a rebalance no longer pauses the whole group. Clients opt in with group.protocol=consumer; the classic protocol stays the client default for now.

Best Practices and Common Pitfalls

✅ Do

  • Key records by the entity whose events must stay in order (orderId)
  • Write events through a transactional outbox when they must match a database change
  • Make every consumer idempotent: an eventId plus a processed-events table or a natural unique constraint
  • Configure a DefaultErrorHandler with a dead-letter topic, mark non-recoverable exceptions as not retryable, and alert on DLT growth
  • Wrap deserializers in ErrorHandlingDeserializer so one malformed record cannot block a partition
  • Name events as past-tense facts and include what consumers need, so they do not call back synchronously
  • Choose the partition count for the consumer parallelism you will need
  • Monitor consumer lag per group — it is the first sign that consumers cannot keep up

❌ Don't

  • Don't call kafkaTemplate.send() inside a database transaction and assume both happen or neither does
  • Don't ignore the CompletableFuture from send() — a rejected record is otherwise invisible
  • Don't share the producer's event class with consumers through type headers; it couples deployments by class name
  • Don't do slow work longer than max.poll.interval.ms inside a listener
  • Don't turn request/response interactions ("is this card authorised?") into events
  • Don't expect ordering across partitions, or after adding partitions to a keyed topic

Interview Questions

🎓 Junior level
What is the difference between a topic, a partition and an offset?

A topic is a named log of records. It is split into partitions, each an ordered, append-only sequence stored on a broker; partitions are what Kafka parallelises and replicates. An offset is the position of a record within one partition, and a consumer group tracks, per partition, the offset it has processed up to.

Why do we send the order id as the record key?

Records with the same key always land in the same partition, and Kafka guarantees order only within a partition. Keying by order id keeps every event of one order — placed, paid, shipped — in the order they were produced, while different orders are spread across partitions and processed in parallel.

What is a consumer group?

A set of consumers sharing a group.id. Kafka assigns each partition to exactly one member, so the group shares the work; different groups each receive every record. Notification and invoicing use different groups, so both see every order.

What does "at-least-once delivery" mean for the code you write?

A record may be delivered more than once — after a crash before the offset commit, a rebalance, or a producer or outbox retry. The consumer has to produce the same result when it sees the same event twice, typically by recording processed event ids.

🔥 Senior level
An order is saved and an OrderPlaced event is sent from the same @Transactional method. What can go wrong, and how do you fix it?

The database and Kafka are separate systems; the Spring transaction covers only the database. If the send succeeds and the transaction then rolls back, consumers react to an order that does not exist. Sending after commit fixes that but loses the event if the process crashes or Kafka is unavailable between commit and send. The standard fix is a transactional outbox: write the event to an outbox table in the same transaction, then publish it with a relay or CDC (Debezium). That gives at-least-once publication, which in turn requires idempotent consumers.

Consumer lag keeps growing and the logs show frequent rebalances. How do you diagnose it?

Frequent rebalances with growing lag usually mean processing a batch exceeds max.poll.interval.ms: the member is evicted, its partitions move, and the batch is reprocessed elsewhere — so work is repeated and little progresses. Check processing time per record against max.poll.records, slow downstream calls inside the listener, and blocking retries with long back-offs. Fixes: smaller batches, faster or asynchronous downstream work, non-blocking retries for long outages, more partitions and consumers if throughput is the real limit. Kafka 4's KIP-848 protocol reduces the cost of each rebalance but not the cause.

A record that can never be deserialised arrives on a partition. What happens with a default setup, and what should happen?

Without ErrorHandlingDeserializer, deserialisation fails inside the consumer before the listener is called; depending on the version and configuration, the container cannot get past that offset and the partition stalls — a poison pill. Wrapping the real deserializer in ErrorHandlingDeserializer turns the failure into a DeserializationException, which DefaultErrorHandler treats as not retryable and sends straight to the dead-letter topic with the original bytes and the exception in the headers.

Does Kafka's exactly-once semantics mean the customer gets exactly one email?

No. Kafka's exactly-once semantics — idempotent producers plus transactions — covers read-process-write loops within Kafka: consuming from one topic, producing to another and committing the offsets atomically. An email, an HTTP call or a database write outside that transaction is a side effect Kafka cannot roll back. For those, the guarantee is at-least-once delivery plus an idempotent consumer, which gives effectively-once results.

Microservices with Spring Boot

Splitting the shop into order, inventory, payment and notification services — when it pays off, why a modular monolith comes first, and how services that no longer share a database or a transaction still agree on what happened to an order

Checked against Spring Boot 4.2 · Spring Modulith 2.2 — November 2026

What Microservices Are — and the Problem They Actually Solve

A microservice architecture splits one application into several, each deployed on its own, owning its own data, and talking to the others only over the network — HTTP calls or events. The shop would become an order service, an inventory service, a payment service and a notification service instead of one ShopApplication.

The problem it solves is organisational before it is technical: several teams changing one codebase block each other's releases. Separate services let the inventory team ship on Tuesday without waiting for the checkout team. The price is that every call between them can now fail, be slow, or arrive twice, and that nothing spans two services in one transaction. Split badly, you pay the price and get none of the benefit:

Start With a Modular Monolith

The hard part of microservices is finding boundaries that hold: if the services you cut keep needing each other's data, you built a distributed monolith. Boundaries are much cheaper to get wrong inside one application. The shop is already organised by feature — order, inventory, payment, notification — and Spring Modulith turns those packages into modules with enforced rules.

If a module later needs its own release cycle or its own scaling, it can be lifted out with its tables and its events, and its listeners become Kafka consumers. Many teams never need that step — a well-modularised monolith is a fine end state.

Where to Cut: Each Service Owns Its Data

A service boundary is a data boundary. Each service owns its tables — no other service reads or writes them — and exposes what others need through its API or its events. That is what makes independent releases possible: inventory can rename a column without coordinating with anyone.

Data another service needs often is copied, not fetched: notification keeps the customer's e-mail address it received in OrderPlaced instead of calling a customer service for every message. That copy can be slightly out of date, and the design has to accept it.

Synchronous Calls: HTTP Service Clients

Some answers are needed immediately — checkout cannot accept an order without knowing the stock was reserved. Spring Framework 7 declares such a client as an interface, and Spring Boot creates and configures the implementation.

Every synchronous call multiplies failure

If checkout calls three services that are each available 99.9% of the time, checkout is available about 99.7% of the time — before counting its own bugs. Keep synchronous chains short, give every call a timeout, and decide what happens when it fails: retry, fall back, or fail fast. That is what Resilience4j adds.

Asynchronous Events and the Outbox

Everything that does not need an immediate answer travels as an event: the order service announces OrderPlaced, and payment and notification react when they can. The Kafka page explains the dual-write problem — saving the order and publishing the event are two writes that can half-fail — and builds a transactional outbox by hand. Spring Modulith provides the same guarantee with its event publication registry: the event is stored in the order's transaction and published to Kafka after commit, retried until it succeeds.

When a Step Fails: Sagas Instead of Distributed Transactions

Placing an order now touches three services, and there is no transaction that spans them. A saga replaces it: a sequence of local transactions, each publishing an event that triggers the next, with a compensating action for every step that has to be undone when a later one fails. The shop's order lifecycle is already one.

StepService and local transactionIf a later step fails

4order: on PaymentCaptured → PAID; on PaymentFailed → CANCELLEDCompensation runs backwards: inventory releases the stock

Between steps the system is briefly inconsistent: an order can be PENDING while its payment is already captured. That is visible and has to be designed for — the order page shows "processing payment" rather than pretending the order is complete. Every listener must also be idempotent, because events can be delivered twice.

Best Practices and Common Pitfalls

✅ Do

  • Start with a modular monolith and enforce the module boundaries (Spring Modulith's verify())
  • Split along business capabilities that already change independently, with one team owning each service
  • Give every service its own data; share it only through APIs and events
  • Prefer events for anything that does not need an immediate answer, published through an outbox
  • Put a timeout on every synchronous call and decide in advance how a failure is handled
  • Model multi-service workflows as sagas with explicit compensations and idempotent listeners
  • Trace requests across services from the first day

❌ Don't

  • Don't split a small application maintained by one team — you take on network failures and eventual consistency for no gain
  • Don't let services read each other's tables or share one database schema
  • Don't build long chains of synchronous calls on the request path
  • Don't use distributed (XA) transactions across services
  • Don't publish events with kafkaTemplate.send() inside the business transaction and hope both succeed
  • Don't share a "common" library of domain classes between services — it couples their releases again

Interview Questions

🎓 Junior level
What is the main benefit of microservices, and what is the main cost?

The benefit is independence: teams can change, release and scale their service without coordinating with everyone else. The cost is that calls between services go over the network — they can fail, time out or be duplicated — and there is no transaction across services, so data is only eventually consistent.

Why should each microservice have its own database?

If two services share tables, neither can change its schema without the other, and their releases become coupled again — the main benefit is lost. Owning the data means other services go through the API or events, which the owning team can keep stable while changing the tables underneath.

When would you use a synchronous HTTP call between services, and when an event?

A synchronous call when the caller needs the answer to continue — checkout needs to know the stock was reserved. An event when other services only need to know that something happened — sending a confirmation or capturing a payment can happen after the order is saved.

🔥 Senior level
What is a distributed monolith, and how do you recognise one?

A system split into several deployables that still cannot change independently: services share a database, call each other in long synchronous chains, or share domain libraries. The symptoms are releases that need several services deployed together, one slow service slowing every request, and an outage in a peripheral service stopping the core flow.

How do you keep data consistent across services without distributed transactions?

Each service commits its own local transaction and publishes an event through a transactional outbox, so the state change and the event either both happen or neither does. Workflows across services become sagas: a sequence of those local steps with compensating actions — cancel the order, release the stock — when a later step fails. Consumers are idempotent because events can be redelivered.

Why recommend a modular monolith before microservices, and what does Spring Modulith add?

Boundaries are the hard part and are cheap to fix inside one codebase. A modular monolith with enforced module rules, communicating through events, gives most of the structural benefit without the operational cost. Spring Modulith verifies module dependencies in a test, provides @ApplicationModuleListener for transactional, asynchronous event handling, keeps an event publication registry so events are not lost, and can externalise events to Kafka when a module is later extracted.

Why is availability lower for a request that calls several services synchronously, and what do you do about it?

Availability multiplies: three dependencies at 99.9% give about 99.7% for the request, and latency adds up the same way. Shorten the chain, replace calls that don't need an immediate answer with events, cache what can be cached, and protect each remaining call with timeouts, limited retries and circuit breakers so one slow dependency does not exhaust every thread.

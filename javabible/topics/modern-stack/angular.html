Angular Frontend for a Spring Boot API

The second client of the shop's /api/orders: a framework with dependency injection, typed HTTP and CSRF handling built in — what changed with signals, and the parts that already match what Spring Boot sends

What Angular Is — and Why It Feels Familiar to a Spring Developer

Angular is a complete frontend framework, written in and for TypeScript. Where React is a view library and you choose the rest, Angular ships the rest: a dependency-injection container, an HTTP client, a router, forms and a test setup, all with one opinion about how to use them. For a team coming from Spring, that is the point — services are injected, configuration is central, and every project looks alike.

The problem it solves is the same as React's: keeping the screen in step with the data. What changed in recent versions is how. Older Angular code is written around RxJS subscriptions and manual flags; Angular 22 reads server data through signals, and most of that code disappears.

Angular or React — What Actually Differs

Both talk to the same Spring Boot API the same way: JSON over HTTP, a session cookie, problem details for errors. The difference is how much is decided for you.

Services and Dependency Injection — the Spring Part of Angular

An Angular service is a class the framework creates once and injects where it is needed — the frontend equivalent of a Spring @Service. Keeping all HTTP calls in one service per resource gives components nothing to do but display, and gives tests one thing to replace.

The response types are the same TypeScript types as on the React page — mirrors of the Java records, ideally generated from the API's OpenAPI description — including the rule that a BigDecimal total travels as a string.

Turning ProblemDetail Errors Into Something the UI Can Show

Unlike fetch, Angular's HttpClient fails on 4xx and 5xx by itself, with an HttpErrorResponse whose error property is the parsed body — the shop's ProblemDetail. An interceptor, Angular's equivalent of a servlet filter, can normalise that for every request in one place.

Local Development: the Angular Dev Server Proxy

ng serve runs on port 4200 and Spring Boot on 8080. As with Vite on the React page, the clean fix for the cross-origin problem is not CORS but a proxy: the browser only talks to 4200, and the dev server forwards /api.

CSRF: Already Wired to What Spring Security Sends

With a session cookie, state-changing requests need a CSRF token. Spring Security 7's csrf.spa() sends the token in an XSRF-TOKEN cookie and expects it back in an X-XSRF-TOKEN header — and those are exactly the names Angular's HttpClient uses by default. It reads the cookie and adds the header to every POST, PUT, PATCH and DELETE sent to a relative URL, so the shop's frontend needs no code for it.

The automatic header only goes to relative URLs

Angular deliberately does not attach the token to absolute URLs such as https://api.shop.example.com/api/orders, so it cannot leak to another host. If the frontend calls the API on a different origin, the header silently stops being sent and every POST fails with 403. Serving both from one origin — as with React — keeps the default working.

Building and Shipping

ng build writes static files to dist/shop-frontend/browser/. They are deployed exactly like the React build: copied into src/main/resources/static and served by Spring Boot, with client-side routes such as /orders/42 forwarded to index.html (see the SpaForwardingController on the React page), or published separately behind the same domain.

Angular's major version every six months

Angular releases a major version roughly every six months and supports each for 18 months. ng update runs migrations that rewrite code — it moved projects to standalone components and the new @if/@for control flow — so staying current is cheaper than jumping several versions at once.

Best Practices and Common Pitfalls

✅ Do

  • Read server data with httpResource and signals in new code; keep RxJS for genuine event streams
  • Put HTTP calls in injectable services, one per API resource, and keep components to display logic
  • Normalise ProblemDetail errors once, in an interceptor
  • Use relative URLs and one origin so HttpClient's XSRF support matches Spring's csrf.spa() without configuration
  • Use the dev-server proxy instead of CORS for local development
  • Run ng update with every major release instead of skipping versions

❌ Don't

  • Don't subscribe() in a component just to copy data into a field — use a resource or the async pipe
  • Don't disable CSRF on the backend because "Angular handles it" — Angular only sends the token the backend issues
  • Don't call the API with absolute URLs to another origin and expect the XSRF header to follow
  • Don't bypass sanitisation with bypassSecurityTrustHtml on API data
  • Don't keep business rules such as prices or stock checks only in the frontend

Interview Questions

🎓 Junior level
What is an Angular service, and how does it compare to a Spring bean?

A class decorated with @Injectable that Angular instantiates and injects where it is requested. With providedIn: 'root' there is one instance for the application, like a singleton Spring bean, and it is the usual place for HTTP calls and shared state.

What is a signal in Angular?

A value that notifies its readers when it changes. Templates and computed values that read a signal are updated automatically when it is set, which lets Angular update only what depends on the changed value.

Why does the Angular dev server need a proxy configuration to call Spring Boot?

Because the dev server (port 4200) and Spring Boot (8080) are different origins. The proxy forwards /api requests server-side, so the browser sees only one origin and no CORS configuration is needed.

🔥 Senior level
Why does an Angular app often work with Spring Security's CSRF protection without any frontend code?

Angular's HttpClient reads a cookie named XSRF-TOKEN and sends its value in an X-XSRF-TOKEN header on mutating requests to relative URLs. Spring Security's SPA CSRF configuration issues the token in that cookie and checks that header, so the defaults line up. It stops working when the frontend calls an absolute URL on another origin, because Angular does not send the token there.

What problems does httpResource solve compared to subscribing to HttpClient in ngOnInit?

It keeps value, loading state and error together in signals, so there are no hand-maintained flags to get out of sync; it cancels the request when its owner is destroyed, so nothing leaks; and it re-runs automatically when signals used to build the URL change, or on reload(). The manual version needs all of that written and tested by hand in every component.

How would you handle API errors consistently across an Angular application talking to a Spring Boot backend?

Make the backend return RFC 9457 problem details for every error (ProblemDetail in Spring), and add an HttpInterceptorFn that maps every HttpErrorResponse to one typed Problem. Components then show detail from the server and handle specific status codes, such as a 409 for out-of-stock, without parsing responses themselves.

A team runs Angular on a CDN domain and the API on another. Which assumptions from a same-origin setup break?

Requests become cross-origin, so the API needs a CORS policy that allows the frontend's origin with credentials; the session cookie needs SameSite=None; Secure to be sent; and Angular stops attaching the XSRF header to absolute URLs, so CSRF needs explicit handling. Routing the API under the frontend's domain avoids all three.

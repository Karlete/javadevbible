Observability for Spring Boot

A customer says checkout took twenty seconds. Metrics tell you it is happening, a trace shows which of the four services spent the time, and the logs of that one request tell you why — if the three are wired together

Checked against Spring Boot 4.2 · Micrometer 1.18 — November 2026

What Observability Is — and Why Logs Alone Stop Being Enough

Observability is being able to answer questions about a running system from the data it emits, without shipping new code to ask them. That data comes in three kinds: metrics (numbers over time: requests per second, error rate, latency percentiles), traces (the path of one request through every service it touched, with timings) and logs (what the code said while handling it).

With one application and one server, logs were enough: you could read them. With the shop split into services, each running several Pods, the log lines of one slow checkout are scattered over a dozen processes with nothing to join them. Spring Boot's answer is Micrometer: one instrumentation API that produces all three signals from the same observation, and stamps every log line with the trace it belongs to.

The Three Signals and the Question Each One Answers

SignalAnswersTypical backendCost
MetricsIs something wrong, and since when? Alerting, dashboards, SLOsPrometheus + GrafanaCheap: aggregated numbers, independent of traffic volume
TracesWhere is the time going in this request, across services?Tempo, Jaeger, or any OTLP backendGrows with traffic, so usually sampled
LogsWhy did this request fail — the details the code recordedLoki, ElasticsearchThe most expensive per request; keep them structured and purposeful

The workflow follows the table: an alert on a metric tells you checkout latency is up, a slow trace from that window shows the time is in the inventory call, and the logs filtered by that trace's id show the reservation retrying against a locked row.

Setting It Up in Spring Boot 4

Spring Boot 4 bundles the OpenTelemetry integration in one starter. Traces — and optionally metrics and logs — are exported over OTLP, the OpenTelemetry protocol that every major backend accepts, usually through an OpenTelemetry Collector running next to the application.

Ten percent is the default, and it is a decision

Spring Boot samples 10% of requests unless told otherwise. That keeps tracing cheap at high traffic, but the one slow checkout a customer complains about has a nine-in-ten chance of not being there. Low-traffic services can trace everything (1.0); high-traffic ones often keep head sampling low and let the Collector keep every slow or failed trace (tail sampling).

Metrics: What You Get, and the Ones Only You Can Add

Without writing any code, the shop already exports http.server.requests (rate, errors and latency per endpoint and status), JVM memory, GC and thread metrics, the HikariCP connection pool, and Kafka producer and consumer metrics. What no framework can know are the business numbers.

High-cardinality tags are the most common metrics mistake

Every distinct combination of tag values is a separate time series. A tag holding an id, an e-mail or a full URL with path variables multiplies them by the number of users or orders. Put per-request detail in traces and logs; keep metric tags to small, fixed sets.

Distributed Tracing: One Request Across Four Services

A trace is a tree of spans: one for the incoming request, children for each database query, HTTP call and message. The trace id travels with the request in the W3C traceparent header, so the inventory service's spans attach to the order service's trace. Spring Boot propagates it automatically through instrumented clients — RestClient, HTTP service clients, WebClient — as long as they are built from the auto-configured builders, not with new.

Kafka joins the trace when observation is enabled on both sides: spring.kafka.template.observation-enabled=true on the producer and spring.kafka.listener.observation-enabled=true on the consumer put the trace context in the message headers and continue it in the listener.

Logs That Belong to a Trace

With tracing on the classpath, Spring Boot puts the current trace and span ids in the logging MDC and adds them to every log line — no code change. A log search for one trace id returns exactly the lines of that one checkout, from every service.

On Kubernetes, write logs to standard output and let the platform collect them, as described on the logging page; with the OpenTelemetry starter they can also be exported over OTLP to the same Collector as traces.

Instrumenting Your Own Code with @Observed

Framework calls are instrumented already; a business operation that spans several of them — "place an order" — is not. @Observed wraps a method in an observation that produces a timer and a span; the Observation API does the same for a block of code.

Observe operations that mean something to the business, not every method: annotating a controller or a repository that Spring MVC and Spring Data already instrument produces duplicate spans and metrics.

Best Practices and Common Pitfalls

✅ Do

  • Set spring.application.name in every service — it is how all three signals are grouped
  • Export through an OpenTelemetry Collector rather than straight to a vendor, so backends can change without redeploying services
  • Alert on metrics (error rate, latency percentiles, saturation), then use traces and logs to investigate
  • Build HTTP clients from Spring's auto-configured builders so trace context propagates
  • Enable observation on Kafka templates and listeners so asynchronous work stays in the trace
  • Use structured logging and include business identifiers such as the order id in the message or as fields
  • Choose the sampling rate deliberately and keep slow and failed traces

❌ Don't

  • Don't tag metrics with ids, e-mails or raw URLs
  • Don't create RestClient or WebClient instances with new — they are not instrumented
  • Don't log personal data or secrets just because the log line now has good context
  • Don't expose every Actuator endpoint publicly; health and prometheus are usually enough, on a protected port
  • Don't add @Observed on code the framework already observes

Interview Questions

🎓 Junior level
What are the three signals of observability, and what is each good for?

Metrics are numbers over time — request rate, error rate, latency — good for dashboards and alerts. Traces follow one request through every service with timings, good for finding where time or errors come from. Logs are the detailed records the code writes, good for understanding why a specific request failed.

What is a trace id, and why does it appear in Spring Boot log lines?

An identifier shared by every span of one request across all services, propagated in the traceparent header. Spring Boot puts it in the logging MDC so every log line written while handling that request carries it, which lets you find all the logs of one request in every service.

What does Micrometer do?

It is the instrumentation API Spring Boot uses: application and framework code record observations through it once, and it turns them into metrics for a backend such as Prometheus and into spans for a tracer such as OpenTelemetry, without the code depending on either.

🔥 Senior level
Why is a high-cardinality metric tag a problem, and where should that detail go instead?

Each unique combination of tag values is a separate time series stored and queried by the metrics backend. A tag such as an order id creates a series per order, which grows without bound, slows queries and can exhaust the backend's memory. Per-request detail belongs in span attributes and log fields; metric tags should have a small, fixed set of values.

A trace stops at the order service even though it calls inventory over HTTP. What would you check?

Whether the client is instrumented: a RestClient or WebClient created with new instead of from the auto-configured builder does not add the traceparent header. Then whether inventory has tracing enabled, whether something in between (a gateway, a proxy) strips the header, and whether the request was simply not sampled.

What are the trade-offs between head sampling and tail sampling?

Head sampling decides at the start of a request, so it is cheap and every service agrees, but it drops interesting traces as readily as boring ones. Tail sampling decides after the trace is complete — usually in an OpenTelemetry Collector — so it can keep every error and every slow request, at the cost of buffering all spans until the decision is made.

How does trace context survive an asynchronous hop through Kafka?

With observation enabled on the KafkaTemplate, the producer writes the trace context into the record headers. With observation enabled on the listener container, the consumer reads those headers and starts its span as a child of the producer's. The consumer may run much later, so the trace shows both the response time and the time until the event was processed.

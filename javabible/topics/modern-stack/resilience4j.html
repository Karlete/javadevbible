Resilience4j: Fault Tolerance for Spring Boot

What checkout does when the inventory service is slow or down — timeouts, retries that are safe to repeat, a circuit breaker that stops hammering a failing service, and a limit on how much one dependency can take down with it

What Fault Tolerance Is — and How One Slow Service Takes Down Another

Fault tolerance is a set of patterns that decide what a service does when something it calls misbehaves: give up after a deadline (timeout), try again (retry), stop calling something that is clearly broken (circuit breaker), and cap how much of the caller one dependency may occupy (bulkhead). Resilience4j is the library that implements them for Java, with annotations and configuration for Spring Boot.

The problem is rarely a dependency that is down — a refused connection fails fast. It is one that is slow. On the microservices page checkout reserves stock by calling the inventory service. When inventory takes 30 seconds to answer, every checkout request waits 30 seconds, requests pile up, and the order service runs out of threads or connections. Inventory's problem has become the whole shop's outage.

Spring Framework 7 or Resilience4j?

Spring Framework 7 added basic resilience to its core: a @Retryable annotation and a @ConcurrencyLimit, enabled with @EnableResilientMethods. For many services that is enough. Resilience4j is still the tool when you need a circuit breaker, rate limiting, or the metrics and health indicators that come with it.

Retry — Only What Is Safe to Repeat

A retry turns a brief glitch — a dropped connection, a Pod being replaced — into a success the caller never notices. It is only safe when doing the operation twice has the same effect as doing it once. Reading the status of a payment is; capturing a payment is not, unless the provider deduplicates by an idempotency key.

Retries multiply load exactly when a service is struggling

Three layers that each retry three times turn one failing request into 64 calls to the bottom service. Retry in one place — usually the caller closest to the user — with a small number of attempts and exponential back-off with jitter, and never retry a call that already timed out because the other side is overloaded.

Circuit Breaker — Stop Calling What Is Broken

A circuit breaker watches the outcome of recent calls. While most succeed it stays closed and lets everything through. When the failure rate passes a threshold it opens: calls fail immediately without reaching the dependency, so the caller stays fast and the failing service gets room to recover. After a wait it lets a few trial calls through (half-open) and closes again if they succeed.

Code review comment

return new ReservationResponse(true);   // fallback: assume it's in stock
throw new InventoryUnavailableException(cause);

A fallback that pretends the reservation worked sells stock we may not have, and nobody notices until the warehouse can't ship. When there is no safe default, the fallback should fail clearly — a 503 the customer can retry is better than an order we can't fulfil.

Bulkheads — How Much One Dependency May Take

A bulkhead caps how many calls to one dependency can be in flight at once. If the recommendation service hangs, at most 20 requests wait on it; the rest fail fast, and checkout — which doesn't need recommendations — keeps its capacity.

Resilience4j's @Bulkhead does the same with a semaphore, or runs the call on its own small thread pool so a hung call cannot even occupy the caller's thread. When several patterns are combined, Resilience4j applies them in a fixed order by default — retry outermost, then circuit breaker, rate limiter, time limiter and bulkhead closest to the call — so every retry attempt is counted by the circuit breaker.

Seeing It Work: Health, Metrics and Events

A circuit breaker that opens silently is half a feature. Resilience4j registers Micrometer metrics for every instance — resilience4j.circuitbreaker.state, resilience4j.circuitbreaker.calls by outcome — and, with registerHealthIndicator: true and management.health.circuitbreakers.enabled: true, adds the state to /actuator/health. Alert on a breaker that stays open, not on each failed call.

Keep circuit breakers out of the liveness probe

An open circuit means a dependency is failing. If its health indicator is part of liveness, Kubernetes restarts the healthy caller — see the Kubernetes page. Leave it in the general health output for dashboards, or in readiness only if a Pod really cannot serve anything without that dependency.

Best Practices and Common Pitfalls

✅ Do

  • Put a connect and read timeout on every outgoing call before adding anything else
  • Retry only idempotent operations, only on transient errors, a few times, with exponential back-off and jitter
  • Use a circuit breaker on calls to other services so a failing dependency fails fast
  • Count slow calls as failures in the circuit breaker — slowness is the common failure
  • Ignore business exceptions (out of stock, validation) in the breaker configuration
  • Make fallbacks honest: a cached or default value only when it is genuinely acceptable, otherwise a clear error
  • Export the metrics and alert on circuits that stay open

❌ Don't

  • Don't retry a payment capture or any non-idempotent call without an idempotency key
  • Don't retry at every layer of a call chain
  • Don't write fallbacks that fake success
  • Don't put the annotations on a method called from the same class — like @Transactional, the proxy is bypassed and nothing happens
  • Don't let a dependency's circuit breaker decide the caller's liveness

Interview Questions

🎓 Junior level
What are the three states of a circuit breaker?

Closed: calls go through and failures are counted. Open: calls fail immediately without reaching the dependency. Half-open: after a wait, a few trial calls go through; success closes the circuit, failure opens it again.

Why is a timeout the first thing to configure on an outgoing call?

Because without it a slow dependency holds the caller's thread or connection for as long as it likes, and requests pile up until the caller fails too. Every other pattern — retry, circuit breaker — relies on calls ending in bounded time.

Which calls are safe to retry?

Idempotent ones, whose repetition has the same effect as a single call — reads, and writes keyed by an idempotency key — and only on transient errors such as connection failures or a 503, not on a 400 or a validation error.

🔥 Senior level
Explain how a slow downstream service can cause a cascading failure, and which patterns stop it.

Each request to the caller waits on the slow dependency, holding a thread, a connection or memory; incoming requests keep arriving, so resources run out and the caller stops answering even requests that don't need the dependency. Its own callers then slow down the same way. Timeouts bound each wait, a bulkhead bounds how many waits there can be, and a circuit breaker stops making the calls at all once the failure rate shows the dependency is unhealthy.

Why can retries make an outage worse, and how do you retry responsibly?

Retries add load exactly when the dependency is overloaded, and retries at several layers multiply: three layers of three retries make 64 calls from one request. Retry in one place, few times, with exponential back-off and jitter so clients don't retry in sync, only on transient errors, and combine it with a circuit breaker so retries stop once the dependency is clearly down.

When should a fallback return a default value, and when should it fail?

Return a default when a degraded answer is genuinely acceptable — no recommendations, or a cached product list. Fail when the operation's result matters for correctness — a stock reservation or a payment — because a fake success creates inconsistent data that surfaces much later. Then the fallback should raise a clear error the client can act on, such as a 503 with problem details.

Spring Framework 7 has @Retryable and @ConcurrencyLimit. Why would you still add Resilience4j?

For the patterns Spring core does not provide: circuit breakers, rate limiters and time limiters, plus the per-instance configuration, Micrometer metrics, health indicators and event endpoints that make them observable in production. A service that only needs simple retries and a concurrency cap can stay with Spring alone.

The Project Behind the Examples

One online shop, one package layout, one set of entities — so an Order on the JPA page is the same Order that Kafka publishes and the REST API returns

Why One Project

Code examples written page by page drift apart. One page has a Customer with a name, the next one a fullName; one order starts as CREATED, another as PENDING; packages are com.shop here and com.company.myapp there. Each example is fine alone, and together they teach the reader that none of the details matter.

So every example on this site belongs to the same application: an online shop that sells products, takes orders, charges payments, issues invoices and emails the customer. This page is its reference. Each topic page still stands alone and shows the code it needs; when it says order/Order.java, this is where that file lives and what is in it.

The shop exists only on these pages. There is no repository to clone: it is a shared vocabulary, not a product.

Package Layout

The base package is com.javadevbible.shop, organised by feature, not by layer: everything about orders sits in order, entity, repository, service and controller together. A change to how orders work touches one package instead of four. File captions on topic pages are relative to the base package, so order/Order.java means com/javadevbible/shop/order/Order.java.

Packages talk to each other through services and events, never by reaching into another package's repository. notification learns that an order was placed from an OrderPlacedEvent; it never queries the orders table.

Every association is LAZY, including the @ManyToOne ones that JPA would otherwise load eagerly. Money is BigDecimal, never double. Timestamps are Instant. Stock is not a column of products: it lives in inventory's stock_levels table, so a price change and a stock movement never compete for the same row lock.

Constructors, getters and the bidirectional helper methods (addItem, addOrder) are left out here; the relationships page shows them and explains why they exist.

Order Lifecycle

An order is created PENDING and moves forward one step at a time. CANCELLED is only reachable before the parcel leaves the warehouse.

StatusMeaningNext
PENDINGPlaced, not yet paidPAID, CANCELLED
PAIDPayment captured; invoice issuedSHIPPED, CANCELLED
SHIPPEDHanded to the carrierDELIVERED
DELIVEREDReceived by the customernone
CANCELLEDStopped before shippingnone

Placing an order publishes an OrderPlacedEvent to Kafka, written through an outbox in the same transaction as the order; the Kafka page builds that flow step by step.
